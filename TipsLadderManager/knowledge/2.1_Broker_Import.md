# 2.1 Broker Import

## Dependencies
**Requires:** TIPS Basics (for CUSIP validation and face value context)
**Feeds into:** 3.0 TIPS Ladder Rebalancing (provides the `holdings` input)

## Purpose
Allows users to upload holdings CSV files instead of manually entering data. Files are auto-detected by format and parsed into a unified `holdings` array consumed by the Rebalance engine.

---

## Supported Formats

### Format 1: Fidelity (`Positions*.csv`)
- **Headers:** Expects columns containing `Account Number`, `Account Name`, `Symbol` (or CUSIP), and `Quantity`.
- **Quantity formatting:** Usually expressed as Face Value (e.g., `10,000`). The parser strips non-numeric characters and divides by 1,000 to convert to Quantity.
- **Account grouping:** Uses `Account Name` (or `Account Number` if name is missing).

### Format 2: Schwab (`*All Accounts*.csv` or single account)
- **Headers:** Expects columns matching `Symbol` and `Qty`.
- **Multi-account structure:** Schwab exports often omit the Account column in the data rows. Instead, they use header blocks: `"[Account Name] ...[Last 4 Digits]"`.
- **Quantity formatting:** Also exports face value. Converted via `Math.round(faceValue / 1000)`.
- **Value column:** Schwab uses `"Mkt Val (Market Value)"` (not `"Current Value"` as Fidelity does). The parser matches either via `c.includes('market value')`. Used to derive per-account TIPS value (slider default) and total account value (slider max).

### Vanguard (name-based CUSIP resolution, via the Format 1/2 broker path)
- **Detection:** Vanguard exports go through the same generic `Symbol`/`Quantity` (or `Qty`/`Shares`) header detection as Formats 1–2 — there is no separate Vanguard-specific format number.
- **CUSIP resolution:** Vanguard's `Symbol` column does not reliably contain the CUSIP, so when the symbol doesn't directly match `tipsMap`, the parser falls back to the `Investment Name` column, which holds a description like `2.125 07/15/33` (coupon %, then MM/DD/YY maturity). It parses that pattern and looks up the CUSIP by `{couponPct}|{year}-{month}` against a reverse index built from `tipsMap` (coupon stored as a fraction internally, so `2.125` matches a stored `0.02125`).
- **Implementation:** `vanguardLookup` in `src/broker-import.js`.

### Format 3: Simple CSV (`cusip,qty`)
- **Structure:** Optional header row (`cusip,qty`), then one row per CUSIP.
- **Quantity:** Total holdings for that CUSIP. No funded/excess distinction.
- **Result:** `{ cusip, qty }` per row. `excessQty` is not set (treated as unknown).
- **Example:**
  ```
  cusip,qty
  91282CPU9,33
  912810QF8,43
  ```

### Format 4: TipsLadderCom CSV (`cusip,qty,year`)
- **Structure:** No header row. Three fields: CUSIP, quantity, funded year.
- **Bracket TIPS appear as multiple rows** — one row per funded year covered (own maturity year + each gap year whose coverage is allocated to that CUSIP).
- **Funded year qty:** The row where field 3 equals the CUSIP's maturity year in `tipsMap`.
- **Excess qty:** Sum of all other rows for the same CUSIP (gap-year cover allocations).
- **Total qty:** Sum of all rows for that CUSIP.
- **Result:** One `{ cusip, qty: total, excessQty }` per CUSIP.
- **Disambiguation:** Detected when the file has no header and field 3 of the first data row is ≥ 2000.
- **Example:**
  ```
  91282CPU9, 8, 2036    ← funded year (8 for own rung)
  91282CPU9, 6, 2037    ← excess cover for gap year 2037
  91282CPU9, 4, 2038    ← excess cover for gap year 2038
  91282CPU9, 1, 2039    ← excess cover for gap year 2039
  912810QF8, 1, 2037    ← upper bracket excess for 2037
  912810QF8, 3, 2038    ← upper bracket excess for 2038
  912810QF8, 4, 2039    ← upper bracket excess for 2039
  912810QF8, 6, 2040    ← upper bracket funded year (6 for own rung)
  ```

### Format 5: Build Export CSV (`cusip,qty,excess` + optional `#fundedYear,dara` block)
- **Structure:** Header row `cusip,qty,excess`, then one row per CUSIP, optionally followed by a per-year DARA metadata block.
- **`qty` field:** Funded year quantity (0 for PLI-zeroed years or if all holdings are excess).
- **`excess` field:** Excess quantity held for gap/future-30Y coverage (0 for non-bracket TIPS).
- **Total qty:** `qty + excess`.
- **Result:** One `{ cusip, qty: total, excessQty }` per CUSIP.
- **Disambiguation:** Detected by the literal header `cusip,qty,excess` (case-insensitive).
- **Example:**
  ```
  cusip,qty,excess
  91282CML2,0,0
  91282CPU9,0,33
  912810QF8,19,24
  912810QP6,20,0
  #fundedYear,dara
  2036,40000
  2037,40000
  ...
  2066,40000
  #params,preLadderInterest=false,maturityPref=last,couponPref=higher
  ```

#### `#fundedYear,dara` block (durable DARA intent — makes the round-trip exact)

Every export from our own app appends this block: a `#fundedYear,dara` marker line followed by one `year,amount` line for **every year in `[firstYear, lastYear]`**, including gap years (2037–2039) and future-30Y years (2057+) that have **no TIPS row**. The value is the resolved per-year DARA the build/rebalance actually used (`summary.daraByYearResolved`).

- **Why:** the held quantities alone do not pin the per-year DARA — build folds later-maturity interest, pre-ladder interest, cover excess, and 2052 AMD into each rung, and PLI-zeroed years show `0,0` which hides their DARA entirely. **Stating** the DARA removes all inference: a build → export → import → rebalance round-trip reproduces the ladder **exactly (zero trades)** for any shape — flat, user-edited per-year (variable), PLI, or future-30Y.
- **Coverage is NOT stored.** Only the per-year DARA (intent) is persisted, never "which TIPS cover which gap/future year." That attribution is recomputed by duration matching at rebalance time, since yields-at-the-time determine the actual trades. (This is deliberately *unlike* the Format-4 funded-years layout, which bakes in cover assignments.)
- **On import (our files):** the block is parsed via `parseFundedYearDaraBlock` into `Map<year, dara>`, fed directly as `daraByYear`; `firstYear`/`lastYear` come from the min/max DARA year (no last-year inference). The load-time per-year DARA population is **bypassed** entirely — the stated DARA is reproduced exactly.
- **Tolerates spreadsheet number formatting.** `parseFundedYearDaraBlock` splits each line with the same quote-aware CSV splitter `broker-import.js` uses for broker files (`parseCSVLine`), then strips everything but digits/`.`/`-` from the amount field. A plan opened, edited, and re-saved in a spreadsheet program — which commonly quotes amounts and adds thousands separators (`"20,000.00"`) — parses the same as a plain `20000`.
- **Backward / forward compatible:** old parsers skip the block (its lines are not valid CUSIP rows); files without the block (broker, legacy Format-5, tipsladder Format-4) populate the per-year DARA panel by **mirroring current holdings** — `computePortfolioARAByYear` raw ARA per in-range year (held = P+I + LMI, empty = incoming LMI), with **no** inference/scaling at load (see 3.0 §Per-Year DARA from Portfolio). A self-financing DARA is solved only if the user selects a range of rungs and clicks **Infer DARA** (3.0 §Per-Rung DARA Selection).

#### `#params` line (construction parameters DARA does not encode)

After the DARA block, our exports append a single `#params,key=value,...` line carrying the
construction parameters that per-year DARA does **not** encode but that still change the target
ladder:

- **`preLadderInterest`** (`true`/`false`) — when on, the pre-ladder coupon pool funds and **zeroes**
  the early rungs; with it off those same years hold real bonds. Two ladders with identical per-year
  DARA but different PLI are *different ladders*, so DARA alone cannot reproduce the target.
- **`maturityPref`** (`last`/`first`/`semiannual`/`all`) — which TIPS a funded year selects: latest-
  or earliest-maturing (one TIPS), Jan+Jul (semiannual, two TIPS out to ~10y), or one TIPS per
  distinct maturity month (`all`, quarterly ≤~2030, Jan/Jul ≤~2035, single Feb 2040+). See 2.0
  §Maturity Selection Within a Funded Year.
- **`couponPref`** (`higher`/`lower`) — for a maturity month with two TIPS issues (different
  coupons — Jan 2027/28/29, Apr 2028/29), which one the ladder buys. Only reachable via
  `maturityPref` values other than `last` (see 2.0 §Maturity Selection Within a Funded Year); the
  UI hides the control entirely for `last` since that policy can never land on a duplicate-issue
  month.
- **`availableCash`** (dollars, default `0`) — cash on hand the ladder is sized down against
  (2.0 §Available Cash). The superseded key `rmdCashOverride` is still **read** as an alias, so
  files written before the ladder-wide generalization keep working; it is never written.
- **`rmdCouponMode`** (`all`/`last`/`none`, default `all`) — the settlement year's
  remaining-coupon-counting choice (2.0 §Settlement-Year Coupon Treatment). Written by both this
  export and the standalone DARA-plan export (2.1 §Standalone DARA-plan file), though the latter
  only emits the line when a value is non-default.

**On import (our files):** parsed via `parseParamsBlock` → `{preLadderInterest, maturityPref,
couponPref, availableCash, rmdCouponMode}`. The file is **authoritative on load** — it sets the
PLI checkbox, maturity preference, coupon pick, Available Cash, and the coupon-counting choice so the reconstruction is exact and
self-contained (no remembering to match a checkbox; this was the cause of the "skipped 2035 / wrong
PLI" symptom). The controls are read live at Run, so a **user override after load wins** (toggling
PLI, or changing first/last year — Available Cash and the coupon-counting choice the same way, via
the ladder parameters and the settlement year's link respectively, 5.0 §Coupon Counting link).
Absent (broker/legacy) → the UI/inference values stand (`maturityPref` defaults to `last`,
`couponPref` to `higher`, `availableCash` to `0`, `rmdCouponMode` to `all`). `maturityPref` is threaded into `runRebalance` → `selectLadderBonds`;
`couponPref` is **Build-only** — `runRebalance`/`runFundedRebalance` never take it and always get
the `selectLadderBonds` default (`higher`), but `parseParamsBlock` still parses it (from a Build
export) so a later re-import into Build reproduces the exact choice.

## Format Detection (Auto)

Detection order:
1. If broker-format keywords are found (`Account Number`, `Positions for`, etc.) → Formats 1 or 2.
2. Else if the first non-empty line matches `cusip,qty,excess` (case-insensitive) → Format 5.
3. Else if the first data row has ≥ 3 comma-separated fields and field 3 is an integer ≥ 2000 → Format 4.
4. Else → Format 3 (simple two-column).

---

## Unified Output: `holdings` Array

All formats produce the same structure passed to the Rebalance engine:

```js
[{ cusip: string, qty: number, excessQty?: number }, ...]
```

- `qty` — total holdings for this CUSIP (funded + excess).
- `excessQty` — excess quantity only (present for Formats 4 and 5; absent for Formats 1–3).

When `excessQty` is present, the engine uses it to initialize `bracketTargetFundedYearQtyBefore[year] = qty − excessQty` for that bracket year, rather than deriving it from DARA math. This preserves the funded/excess split from the prior build across a rebalance cycle.

---

## Process Flow

1. **File Selection (`index.html`)**: Choosing **CUSIP/Qty** on the Import menu (`#import-menu-btn`, 6.0 §Import/Export Menus) clears `#holdings-file.value` before triggering `.click()`, so the browser `change` event fires even when the same file is selected again. When the `change` event fires, the file is read via the browser `File` API.
2. **Auto-Detection**: The first 20 lines are scanned. Broker-specific keywords route to `parseBrokerCSV`. Remaining formats are distinguished by header and field-count rules above.
3. **Extraction & Validation (`src/broker-import.js` for Formats 1–2; inline for Formats 3–5)**:
   - Formats 1–2: Skips non-TIPS assets by validating symbols against the live `tipsMap`.
   - Formats 3–5: Validates CUSIPs against `tipsMap`; skips unrecognized CUSIPs.
   - Format 4: Uses `tipsMap` to determine each CUSIP's maturity year and classify rows as funded vs. excess.
4. **Selection Modal (Formats 1–2 only)**: If > 1 account is found, `#account-overlay` appears with checkboxes for each account (all checked by default). Users can deselect individual accounts or click **"Clear all"** to deselect all accounts at once, then "Import Selected" to proceed.
5. **Handoff**: Holdings are merged (summing quantities of identical CUSIPs) and passed into `runRebalance`.

## CusipQty Export (Build / Rebalance)

The **CUSIP/Qty** option on the Export menu (`#export-menu-btn`, 6.0 §Import/Export Menus) produces a **Format 5** file from both Build and Rebalance output. This file can be directly re-imported into the Rebalance tab on the next rebalancing cycle.

- **Build mode:** `qty` = `fundedYearQty`, `excess` = `excessQty` from the build details.
- **Rebalance mode:** `qty` = `fundedYearQtyAfter`, `excess` = `excessQtyAfter` from the rebalance details.
- Zero-quantity rows for PLI-zeroed years are included (as `qty=0,excess=0`) so the rebalance engine knows these rungs exist at zero cost.
- The `#fundedYear,dara` block (above) is appended from `summary.daraByYearResolved` so the re-import is an **exact, zero-trade round-trip**. This holds the durable per-year DARA intent — consistent with the per-year DARA shown in the Build and Rebalance UI — so the CSV and the UI carry the same information.

## Standalone DARA-plan file (portable persistence, independent of holdings)

**Problem this solves:** the CusipQty export above only reproduces a DARA plan exactly when
re-importing *that same export* — but a real rebalancing cycle re-uploads a **fresh broker file**
(Vanguard/Fidelity/Schwab) each time, which never carries a `#fundedYear,dara` block (or any DARA
data at all) to overlay a plan onto. File load therefore always mirrors the fresh holdings with no
memory of a prior session's per-year shape (3.0 §Per-Year DARA from Portfolio). The standalone plan
file is the portable fix: it carries **only** the DARA intent, with **no CUSIP rows**, so it can be
exported once and re-applied on top of any subsequent fresh holdings upload, on any device.

**Structure:** the same `#fundedYear,dara` marker + `year,amount` lines used inside a Format-5
CusipQty export (§`#fundedYear,dara` block above), but as the *entire* file:

```
#fundedYear,dara
2026,40000
2027,40000
...
2050,20000
```

- **Export** (the **DARA Plan** option on the Export menu, `#export-menu-btn` — 6.0 §Row 1 / §Import/Export
  Menus): writes the *current* `_daraByYearStore` (every year in the panel, sorted) to a downloadable
  CSV. No CUSIP/qty data — this file says nothing about holdings, only about DARA intent. Also
  appends a `#params,availableCash=...,rmdCouponMode=...` line (2.0 §Available Cash,
  §Settlement-Year Coupon Treatment) when either is non-default — omitted entirely otherwise, so a
  plan saved without touching either is a plain `#fundedYear,dara` file.
- **Import** (the **DARA Plan** option on the Import menu, `#import-menu-btn` — 6.0 §Row 1 / §Import/Export
  Menus): parsed via `parseFundedYearDaraBlock` (it only
  looks for the marker line, so it works with or without preceding CUSIP rows — the same parser
  Format-5 imports use). The real prerequisite is `_panelYearRange` being populated — in Rebalance
  that means holdings already loaded, in Build it means a Last Year (and optionally First Year)
  already chosen — since the import **overlays** the plan onto whatever year range is currently
  displayed, it does not select or replace holdings. Years in the plan outside the current range
  are silently not displayed (the panel's range always comes from the loaded holdings or, in Build,
  the chosen year dropdowns — never from the store); years in range but absent from the plan fall
  back to the scalar DARA field, same as any other per-year gap. Sets `_daraLoadedSnapshot` to the
  imported map — the import is the user's new stated intent, honored the same way an explicit
  `#fundedYear,dara` block from our own export is (§Per-Year DARA from Portfolio, no Run-time
  scale; `_daraLoadedSnapshot` itself is internal bookkeeping only, 3.0 §No edit history). Also
  parses a `#params` line if present and applies `availableCash`/`rmdCouponMode` (2.0 §Available
  Cash, §Settlement-Year Coupon Treatment); absent → both reset to their defaults (`0`/`all`), same
  as a fresh holdings load.
- **Not the same file as CusipQty export.** A CusipQty export (`cusip,qty,excess` header) is a
  *holdings* file that happens to carry the DARA block as metadata; a standalone plan file has no
  header and no CUSIP rows at all — the two are detected differently (2.1 §Format Detection: Format
  5 keys off the `cusip,qty,excess` header, which a standalone plan file never has) and serve
  different jobs (reproduce a whole ladder vs. carry just the DARA intent across a fresh re-upload).
- **No same-device cache.** An earlier localStorage "Save DARA Plan" cache offered to auto-apply a
  remembered plan on every matching load; it surfaced its "saved plan found" prompt often enough to
  be more annoying than useful and was removed. The standalone file above is the only persistence
  mechanism now — used deliberately, not offered automatically.
