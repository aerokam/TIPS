# 4.0 Computation Modules

## Dependencies
**Requires:** TIPS Basics, 2.0 TIPS Ladders, 3.0 TIPS Ladder Rebalancing

**This file specifies the module interfaces for shared computation libraries.**
The underlying math is defined in the files above; this file defines function contracts,
input/output shapes, and which spec section each function implements.

---

## Purpose

Shared modules eliminate duplicated formula code across `rebalance-lib.js` and `build-lib.js`.
Each function has a single authoritative implementation. Both orchestrators import from these modules.

Traceability: every function maps to a spec formula. If a computed value is wrong, check the
spec formula first, then the function implementation.

## bond-math.js

Pure per-bond calculations. No ladder state, no running pools. Given a bond and refCPI, returns
all derived per-bond quantities. Formulas defined in **2.1 TIPS Basics**.

### `bondCalcs(bond, refCPI)`

**Inputs:**
- `bond` — `{ price, coupon, baseCpi, maturity: Date }`
- `refCPI` — number (settlement date reference CPI)

**Returns:**
```
{
  indexRatio,        // refCPI / bond.baseCpi                        → 2.1 Index Ratio
  principalPerBond,  // 1,000 × indexRatio                           → 2.1 Inflation-Adjusted Principal
  costPerBond,       // price/100 × indexRatio × 1,000               → 2.1 Cost per Bond
  nPeriods,          // 1 if maturity month < 7, else 2              → 2.1 Last-Year Interest (TIPS)
  couponPerPeriod,   // bond.coupon / 2
  ownRungInt,        // principalPerBond × couponPerPeriod × nPeriods → 2.1 Last-Year Interest (TIPS)
  piPerBond,         // principalPerBond + ownRungInt                 → 2.1 P+I per Bond (TIPS)
  annualInt,         // principalPerBond × bond.coupon               → 2.1 Inflation-Adjusted Annual Interest
}
```

**Note:** `piPerBond` here equals `principalPerBond × (1 + coupon/2 × nPeriods)` — algebraically
identical to `adjustedPrincipal + lastYearInterest`. Both forms are valid; see 4.0 Named Quantities.

---

### `calculateDuration(settlement, maturity, coupon, yld)` → Macaulay Duration

Returns Macaulay duration in **years**, or `null` if inputs are degenerate.

**Convention:** Actual/Actual day count, semi-annual compounding (frequency = 2). Matches Google Sheets `DURATION(settlement, maturity, coupon, yld, 2, 1)`.

**Guard conditions:**
- Returns `null` if `settlement >= maturity`
- Returns `null` if `yld ≤ −2` (prevents division by zero in `1 + yld/2`; negative yields between −2 and 0 are **valid** — not filtered out)

**Algorithm:**

1. Find `nextCpn` = first coupon date on or after `settlement` (semi-annual schedule aligned to maturity month and day).
2. Find `lastCpn` = `nextCpn` minus one semi-annual period.
3. Compute period variables:
   - `E   = days(lastCpn, nextCpn)`    — length of current coupon period in days
   - `DSC = days(settlement, nextCpn)` — days from settlement to next coupon
   - `w   = DSC / E`                   — fractional first period (0 < w ≤ 1)
4. Enumerate coupon dates `nextCpn, nextCpn+1period, …` up to and including `maturity`. Let `N` = count.
5. For each period index `j = 0, 1, …, N−1`:
   - `t_j  = w + j`                              — time to payment, in semi-annual periods
   - `CF_j = coupon/2 × 1000`                   — semi-annual cash flow (per $1,000 face)
   - Final period adds principal: `CF_{N-1} = coupon/2 × 1000 + 1000`
   - `PV_j = CF_j / (1 + yld/2)^{t_j}`
6. Return `Σ(t_j × PV_j) / Σ(PV_j) / 2`

The final `/ 2` converts from semi-annual periods to years.

**Used in:** `calcGapParams` (synthetic gap durations), bracket weight calculations (Phase 3b).

**Implementation:** a thin wrapper — `return calculateDurationDetail(settlement, maturity, coupon, yld)?.macaulay ?? null`.

---

### `calculateDurationDetail(settlement, maturity, coupon, yld)` → Macaulay Duration workings

The single implementation of the algorithm above; `calculateDuration` and every synthetic-duration
caller in `gap-math.js` (`gapParamsCore`, `future30yParamsCore`) get their number from this function,
never a second copy of the walk. Returns `null` under the same guard conditions as `calculateDuration`.

**Returns:**
```
{
  nextCpn, lastCpn,   // Date — the coupon-date pair the walk starts from
  E, DSC, w,          // day-count fractions (algorithm steps 2–3 above)
  periods,            // [{ date, t, cf, pv }] — one entry per coupon date (algorithm step 5)
  macaulay,           // Σ(t × PV) / Σ(PV) / 2 — same value calculateDuration returns
}
```

**Used in:** 5.0 §Nested (Level-3) drills `gapdur-<year>` / `f30dur-<year>` — the only consumer that
needs the intermediate workings rather than just the final number; every other caller still goes
through `calculateDuration`/`calculateMDuration`.

---

### `calculateMDuration(settlement, maturity, coupon, yld)` → Modified Duration

```
mac = calculateDuration(settlement, maturity, coupon, yld)
return mac != null ? mac / (1 + yld/2) : null
```

**Spec reference:** 2.1 TIPS Basics §Duration (definition) and §Yield Calculation Conventions (Actual/Actual, semi-annual). Used in: 4.0 Phase 2 (synthetic gap durations), Phase 3b (bracket durations), WAD.

---

### `couponSchedule(settle, maturity)` — coupon payment dates

```
nextCpn = first coupon date on or after settle (same schedule as calculateDuration)
dates   = [nextCpn, nextCpn + 1 period, …] up to and including maturity
```

**Returns:** array of `Date`, earliest first; `[]` if no coupon date exists on or before `maturity`
(mirrors `calculateDuration`'s guard). The final entry always equals `maturity` — the coupon-date walk
never produces a date past it, and principal is repaid the same day as the last coupon.

Reuses `_nextCouponOnOrAfter` (the same coupon-date finder `calculateDuration`/`yieldFromPrice`/
`priceFromYield` use) so a held TIPS's payment dates here always agree with its duration/yield
calculations elsewhere. **Used in:** 5.0 §Cash Flow Calendar.

---

### `accruedInterest(coupon, settle, mature)` — day-count proration

```
nextCoupon, lastCoupon  // semiannual schedule aligned to maturity month/day (same schedule as calculateDuration)
E   = days(lastCoupon, nextCoupon)   // days in the current coupon period
A   = days(lastCoupon, settle)       // days elapsed since the last coupon
accrued = (coupon/2 × 100) × (A / E) // per $100 par, nominal — no index ratio applied
```

**Returns:** `{ accrued, A, E, lastCoupon, nextCoupon }`.

**Spec reference:** 1.0 Bond Basics §Accrued Interest (Actual/Actual day count, matches Treasury/broker settlement convention — NOT a flat half-coupon; this function returns the general nominal formula, no index ratio — TIPS callers apply the index ratio themselves per 2.1 TIPS Basics §Accrued Interest). This is the single authoritative accrued-interest implementation: `yieldFromPrice` and `priceFromYield` both call it (previously each duplicated the A/E/accrued calc inline), and the Trade Ticket's Accrued Interest column (5.0 §Trade Ticket) calls it directly. To get real, index-ratio-adjusted dollars per bond: `accrued/100 × indexRatio × 1000`.

---

### `rungAmount(qty, piPerBond, laterMatInt)`

```
rungAmount = qty × piPerBond + laterMatInt
```

**Spec reference:** 4.0 Phase 5 ARA After formula. Also the structure of `fy_amt` in build-lib.
Ensures the `laterMatInt` term is never omitted in amount calculations.

## gap-math.js

Gap year analysis and bracket sizing. Formulas defined in **4.0 Phase 2 and Phase 3**.

### `interpolateYield(anchorBefore, anchorAfter, targetDate)`

Linear yield interpolation between two anchor bonds.

```
yield = anchorBefore.yield +
        (targetDate - anchorBefore.maturity) × (anchorAfter.yield - anchorBefore.yield) /
        (anchorAfter.maturity - anchorBefore.maturity)
```

**Spec reference:** 4.0 Phase 2, 3.0 Synthetic TIPS Construction.

---

### `syntheticCoupon(yield)`

```
syntheticCoupon = MAX(0.00125, FLOOR(yield × 100 / 0.125) × 0.00125)
```

**Spec reference:** 4.0 Phase 2, 3.0 Synthetic TIPS Construction.

### `calcGapParams(gapYears, tipsMap, settlementDate, refCPI, dara, effectivePrelim, pliCreditByGapYear?)`

For each gap year (long→short): interpolate yield → synthetic coupon → synthetic maturity (Jan 15) →
MDURATION → gap qty estimate.

**`effectivePrelim`** — the prelim map passed to this function must reflect actual purchasing intent:
- When `preLadderInterest` is active, zeroed funded years must have their `annualInterest` set to `0` before being passed in. Zeroed funded years have no actual TIPS purchased, so they generate no coupon income and must not contribute to gap year LMI.
- Non-zeroed funded years pass through unchanged.

**`pliCreditByGapYear`** *(optional)* — map of `{ year → pliCredit }` for remaining PLI pool after funded year zeroing, distributed short→long across gap years per **2.0 §Gap Parameter Calculation PLI gap year pass**. Omit (or pass empty) when `preLadderInterest` is disabled.

**Returns:**
```
{
  avgDuration,  // cost-weighted mean of synthetic durations: Σ(qty·dur)/Σ qty (fallback simple mean if Σ qty=0) → 2.0 Gap Avg Duration
  totalCost,    // sum of (gapQty × costPerBond) across all gap years (synthetic costPerBond = $1,000)
  breakdown,    // per-year: { year, qty, piPerBond, laterMatInt, dur, synYld, synCpn, durDetail }
  anchors,      // { before, after } — the two anchor bonds interpolateYield used (§interpolateYield below)
}
```

`synYld`/`synCpn`/`durDetail` are the interpolated yield, the synthetic coupon derived from it, and
`calculateDurationDetail`'s full Macaulay workings for that year's synthetic TIPS — carried on the
breakdown entry purely for the Level-3 duration drill-down (5.0 §Nested (Level-3) drills
`gapdur-<year>`); no other consumer reads them. `anchors.before`/`anchors.after` are each
`{ maturity, yield }`, the same objects `interpolateYield` was called with.

**Spec reference:** 2.0 §Gap Parameter Calculation.

---

### `bracketWeights(lowerDuration, upperDuration, avgGapDuration)`

```
rawLowerWeight = (upperDuration - avgGapDuration) / (upperDuration - lowerDuration)
lowerWeight = CLAMP(rawLowerWeight, 0, 1)
upperWeight = 1 - lowerWeight
```

Weights are shares of the block cost and can never be negative or exceed 1. When
`avgGapDuration` falls outside `[lowerDuration, upperDuration]` — e.g. a deep-discount,
near-zero-coupon cover durations out past a higher-coupon block average — the raw solve would
put a bond at negative or >1 weight; clamping puts the whole block on the nearer cover instead
and accepts a larger duration-match delta.

**Returns:** `{ lowerWeight, upperWeight }`

**Spec reference:** 4.0 Phase 3c.

---

### `bracketWeightsN({ retained, dActive, dUpper, dGap, totalBlockCost })`

Generalizes `bracketWeights` to price [Retained Bracket Excess](../../knowledge/DATA_DICTIONARY.md#retained-bracket-excess)
at each retained maturity's **own** duration, rather than at the active lower bracket's (which
under-matches the gap since retained maturities are shorter). `retained` is an oldest-to-newest
array of `{ duration, excessCost }`. Only the active lower bracket and the upper bracket are solved;
retained legs are frozen inputs:

```
R   = Σ (retained[i].excessCost / totalBlockCost)
D_R = Σ (retained[i].excessCost / totalBlockCost) × retained[i].duration

upperWeight  = ((dGap - D_R) - (1 - R) × dActive) / (dUpper - dActive)
activeWeight = (1 - R) - upperWeight
```

If `activeWeight` solves negative, the lower side is carrying more than the block needs. Rather
than depleting the earliest retained leg outright, solve for the **exact weight of that leg**
that brings `activeWeight` back to 0 (holding every other retained leg fixed):
```
wᵢ = (dGap − D_fixed − (1 − R_fixed) × dUpper) / (dᵢ − dUpper)
```
where `R_fixed`/`D_fixed` exclude leg `i`. Clamp to `[0, currently held]` and re-solve. Only if
depleting leg `i` entirely is *still* not enough does the next-earliest leg get the same
treatment. Selling a whole leg when a partial sale would restore the match is needless trading —
not the rule (2.0 §Retained Bracket Excess). With every retained leg sold this reduces to the
plain two-sided case, which always has a solution when `dGap` sits between `dActive` and `dUpper`;
`feasible` is only a guard for degenerate inputs (coincident durations, or `dGap` outside that span).

**Returns:** `{ retainedWeights, activeWeight, upperWeight, feasible, sold }`

**Spec reference:** 2.0 §Retained Bracket Excess. Currently called from `rebalance-lib.js`'s
3-bracket path with a single retained leg (see 3.0 §Retained Maturities); the function itself
supports any number of legs.

---


### `bracketExcessQtys(totalCost, lowerWeight, upperWeight, lowerCostPerBond, upperCostPerBond)`

```
lowerExQty = ROUND(totalCost × lowerWeight / lowerCostPerBond)
upperExQty = ROUND(totalCost × upperWeight / upperCostPerBond)
```

**Returns:** `{ lowerExQty, upperExQty }`

**Spec reference:** 4.0 Phase 3c (`targetExcess$ per bracket = gapTotalCost × bracketWeight`),
4.0 Named Quantities `excessQtyAfter`.

---

### `gapParamsWithUpperFeedback(args)`

Shared wrapper around `gapParamsCore` that credits the **upper-bracket (2040) excess coupon** into
gap sizing via a fixed-point iteration. Called by BOTH adapters — `calcGapParams` (build, ladder-core)
and `calculateGapParameters` (rebalance) — so equal inputs produce equal output and the build↔rebalance
round-trip stays exact.

`args` are the `gapParamsCore` args **plus** `refCPI` and optional `creditUpperExcess` (default `true`).

```
resolve bracket bonds from tipsMap (lower = latest-maturing TIPS < minGapYear; upper = nearest Feb TIPS > maxGapYear)
extra ← 0
repeat (≤ 6×):
    lmi ← lmiAboveByYear with lmi[upperYear] += extra
    params ← gapParamsCore({ ...args, lmiAboveByYear: lmi })
    upperWeight ← bracketWeights(lowerDur, upperDur, params.avgDuration).upperWeight
    upperExQty  ← ROUND(params.totalCost × upperWeight / upperCostPerBond)
    newExtra    ← upperExQty × (1000 × indexRatio × upperCoupon)     // annual excess coupon, real $
    if newExtra == extra: break        // fixed point — params already reflects it
    extra ← newExtra
return params
```

**Why:** the upper-bracket excess matures after the gap, so its coupon is paid through the gap years
and — like every other rung's coupon — must size the gap synthetic quantities down. But `upperExQty`
is sized *from* the gap cost, so the dependency is circular; it contracts to a fixed point in ~2 steps
(the term is ~1% of gap cost). Falls back to plain `gapParamsCore` when bracket bonds can't be resolved
or `creditUpperExcess` is false. The lower bracket (2036) matures before the gap and never feeds it.

**Spec reference:** 2.0 §Gap Year Coverage Model (Upper-bracket coupon feedback).

## build-lib.js — Pre-Ladder Interest Option

**Option:** `preLadderInterest` (boolean, default `false`)

When `firstYear > settlementDate.getFullYear()` and the option is enabled, coupon payments
received from all ladder bonds BEFORE the ladder starts is credited against the earliest
funded years, potentially eliminating the need for TIPS in those years.

### Algorithm

**Step 1 — Prelim sweep** (unchanged, long→short): produces `prelim[year].annualInterest`
and `prelim[year].laterMatInt` for all funded years.

**Step 2 — Compute pre-ladder pool**
```
preLadderYears = max(0, firstYear - settlementDate.getFullYear())
totalAnnualInt = Σ prelim[year].annualInterest  (all years in ladder)
preLadderPool  = preLadderYears × totalAnnualInt
```
The pool represents total coupon payments from all ladder bonds received in the calendar years
[settlementYear, firstYear−1]. It is computed from prelim quantities — the approximation is
slightly conservative (pool may be modestly over-estimated if some years are zeroed).

**Step 3 — Single interleaved PLI pass (short→long across ALL year types):**
Funded years and gap years are processed together in maturity order. Gap years consume pool before longer-dated funded years — e.g., 2037–2039 are processed before 2040, so whether 2040 is zeroed depends on what the gap years left behind.
```
remaining = preLadderPool
pliCreditByGapYear = {}
for year in (rangeYears ∪ gapYears) ascending:
  if year is a funded year:
    need = MAX(0, DARA - prelim[year].laterMatInt)
    if remaining >= need:
      zeroedYears.add(year); remaining -= need
    else:
      partialCredit = remaining; remaining = 0; break
  if year is a gap year:
    // Use full prelim LMI for funded years above — synth LMI from longer gap years
    // not yet known; this is an accepted approximation for PLI distribution purposes
    actualTIPSLMI = sum(prelim[y].annualInterestReal for funded year y > year)
    need = MAX(0, DARA - actualTIPSLMI)
    if remaining >= need:
      pliCreditByGapYear[year] = need; remaining -= need
    else:
      pliCreditByGapYear[year] = remaining; remaining = 0; break
```
After this pass, `zeroedFundedYears` is fully determined — including whether bracket years like 2040 are zeroed.

**Step 4 — Build effective prelim for gap calculation:**
Zero out `annualInterestReal` for all `zeroedFundedYears` before passing prelim to `calcGapParams`.
This ensures gap year LMI reflects only coupon income from TIPS that will actually be purchased.

**Step 5 — Final output:** for each funded year:
- `fundedYearQty = 0` if year ∈ zeroedYears
- `fundedYearQty = max(0, ROUND((DARA - laterMatInt - partialCredit) / pi))` for the partial credit year
- Normal `fyQty(DARA, laterMatInt, pi)` for all subsequent years

Bracket `excessQty` is computed normally and applied on top regardless of zeroing —
duration matching still applies to bracket years even if their funded-year qty is zero.

**Summary fields added when `preLadderInterest` enabled:**
- `preLadderYears` — calendar years before ladder start
- `preLadderPool` — total pre-ladder coupon pool ($)
- `zeroedFundedYears` — array of years with fundedYearQty = 0

## build-lib.js / rebalance-lib.js — Future 30Y Cover AMD

When `lastYear > 2056`, the accrued market discount on the excess cover holdings is counted as an additional income source. **Both Future 30Y covers carry AMD** — the 2052 upper and the 2056 lower (each a deep-discount, near-zero-coupon TIPS). See **2.0 §Future 30Y Cover AMD** for the full definition and rationale.

AMD is **interest on the full held excess position**, modeled **held-to-maturity** (this is **Option C** — even, not depleted by sales). The 2052 is near-zero-coupon, so its yield arrives as accretion; income each year = `future30yUpperExQty × a(Y)`, where `a(Y)` is that year's per-bond accretion increment on the **full, undepleted** excess — exactly like a coupon earned on the whole position. Selling some 2052s only realizes the cash; it does not reduce the income basis. Applies to **excess holdings only** — funded-year 2052s are held to maturity and receive par, so their discount is realized at maturity and already captured in P+I (counting AMD on them would double-count).

**Computed once before the Phase 4 sweep** (after `future30yParams`, the cover durations, and the cover excess quantities are known) by `excessAmdSchedule({ bond, exQty, refCPI, settlementYear })` in `gap-math.js` — a **generic per-bond** schedule (nothing 2052-specific). `sizeLadder` keeps an `amdExcessBonds` list (today `[{ 2052 upper cover }, { 2056 lower cover }]`; add the near-par 2036/2040 gap brackets here later), sums each bond's schedule into the combined `future30yUpperAnnualAmdByYear` (sizing) and records each bond's lifetime AMD in `amdLifetimeByBracketYear` (the cover-Amount net-out, keyed by bracket year). Rebalance rebuilds the **Before-state** AMD per cover from each cover's *actual held excess* (held proportions need not match the target split). Builds a `Map<year → amd$>` via the constant-yield method (imports `priceFromYield` from bond-math.js):

```
indexRatio_settle = refCPI / bond.baseCpi
costPerBond       = bond.price / 100 × indexRatio_settle × 1000
parPerBond        = indexRatio_settle × 1000          // redemption value, settlement-real dollars
matYear           = bond.maturity year

// adjPrice(Y): constant-yield real price at last calendar day of Feb (new Date(Y, 2, 0))
adjPrice(Y) = (date(Y) >= maturity) ? parPerBond
            : priceFromYield(yield, coupon, new Date(Y,2,0), maturity) / 100 × indexRatio_settle × 1000

// Walk EVERY year settlement+1 → matYear: income = full excess × this-year's accretion; basis steps up.
// No roll, no depletion — the held quantity is constant.
prevAdj = costPerBond
for year in (settlementYear+1 .. matYear):
  ap = adjPrice(year)
  byYear.set(year, exQty × (ap − prevAdj))     // exQty × a(Y)
  prevAdj = ap
```

**Cover-roll coupon (`future30yRollCoupon`).** After the 2052 matures, its cost basis is rolled into the actual Future-30Y TIPS; their coupon (upper-cover share) credits the funded years between the 2052 maturity and the first Future-30Y year (2053–2056). Built in `sizeLadder` as `future30yRollCouponByYear`:
```
rollAnnual = future30yUpperWeight × future30yParams.future30ySeedLMI
for year in (upperMatYear+1 .. min(future30yYears)−1): set(year, rollAnnual)
```
Threaded **identically to AMD** and combined with it via `calcFuture30yExtraIncome(Y) = AMD(Y) + rollCoupon(Y)` for all sizing. Rebalance has the same map plus `calcFuture30yRollCouponForQty(Y, qty)` (Before-state scale) and a held-based equivalent in the DARA-recovery path (`heldUpperExcess × costPerBond_2052 × syntheticCoupon(yield_2056)`).

**Cover Amount net-out.** The bracket/cover Amount nets its own lifetime AMD out of P+I and adds the intra-block coupon back so the cover total ≈ `numFuture30yYears × DARA` (see 2.0 §Excess Amount):
```
excessAmt_b = excessQty_b × pi_b − amdLifetimeByBracketYear.get(b) + weight_b × future30yLMITotal
future30yLMITotal = Σ future30yParams.breakdown[].laterMatInt        // intra-block coupon, gap-LMI analog
```

**Per funded year Y** (called inside the Phase 4 sweep):

```
function future30yUpperAnnualAmd(Y):        // build
  return amdByYear.get(Y) ?? 0

function future30yUpperAnnualAmdForQty(Y, qty):   // rebalance — scales for before/after holdings
  if future30yUpperExQty <= 0: return 0
  return (amdByYear.get(Y) ?? 0) × qty / future30yUpperExQty
```

The profile is **even, gently back-loaded by convexity**: `a(Y)` rises modestly toward maturity while the held quantity stays constant, so the annual AMD is roughly level with a gentle upward tilt. **Conserving:** `Σ a(Y) = parPerBond − costPerBond_2052`, so lifetime AMD per bond equals the total market discount exactly.

**fyQty formula with AMD + roll coupon** (replaces plain `fyQty` for years where either is > 0):

```
fyQty(Y) = MAX(0, ROUND((dara − runningLMI − future30yUpperAnnualAmd(Y) − future30yRollCoupon(Y)) / piPerBond))
```

**Pre-Ladder Interest integration:** When `preLadderInterest` is enabled, the pool is built from two **named, separately-stored** sources so the credit stays traceable:
```
preLadderCouponPool     = preLadderYears × Σ prelim[Y].annualInterest          // coupon interest
preLadderAmdPool        = Σ future30yUpperAnnualAmd(Y)  for Y in [settlementYear, firstYear)
preLadderRollCouponPool = Σ future30yRollCoupon(Y)      for Y in [settlementYear, firstYear)  // 2053–56 if ladder starts later
preLadderPool           = preLadderCouponPool + preLadderAmdPool + preLadderRollCouponPool
```
`preLadderCouponPool`, `preLadderAmdPool`, and `preLadderRollCouponPool` are exported on the summary (build and rebalance) and consumed by the Level-3 "Pre-ladder pool composition" drill (`buildPreLadderPoolDrill`). The zeroing condition for funded year Y uses the in-ladder extra income (AMD + roll coupon):
```
need = MAX(0, DARA − prelim[Y].laterMatInt − future30yUpperAnnualAmd(Y) − future30yRollCoupon(Y))
```

**Rebalance:** `amdByYear` is built once from the rebuilt (`after`) `future30yUpperExQty` partition. The before-state sweep uses `future30yUpperAnnualAmdForQty(Y, qtyBefore)` (linear scale by held qty); the after-state Phase 4 sweep uses `future30yUpperAnnualAmdForQty(Y, future30yUpperExQty)` = the full schedule.

**Pre-ladder range guard:** `amdBefore` and `amdAfter` are 0 for years outside `[firstYear, lastYear]`. Pre-ladder AMD (years `[settlementYear, firstYear)`) flows only via PLI pool — it does NOT appear as ARA for those years.

**AMD-driven rebalance years:** Any AMD year **or roll-coupon year** Y within `[firstYear, lastYear]` with `future30yUpperExQty > 0` is added to `rebalYearSet` regardless of method (Gap or Full). This ensures both credits reduce the funded-year qty and trigger actual selling in both modes, preventing `amtAfter > DARA`. The range is the full AMD schedule (`settlement+1 → 2052 maturity`) plus the roll-coupon years (2053–2056), not a hardcoded cap. The rebalance target-sizing `needed` subtracts `calcFuture30yUpperAnnualAmd(Y) + calcFuture30yRollCoupon(Y)` so a build→rebalance round-trip stays zero-trade through these years.

**PLI-zeroed year sell-all rule:** When the PLI pool fully covers a funded year's need, the target CUSIP qty is set to 0 AND all older TIPS in that same year (if the portfolio holds multiple TIPS maturing the same year) are also sold to 0. Without this, those older holdings remain in the portfolio and their principal+interest appears as phantom income in that year's "Amount After" column.

**Summary fields:**
- `future30yUpperAnnualAmdByYear` — `Map<year → amd$>` (combined AMD schedule) for display/inspection
- `future30yLMITotal` — intra-block coupon added back to the cover Amount
- `preLadderCouponPool`, `preLadderAmdPool`, `preLadderRollCouponPool` — the named components of `preLadderPool`, for the pre-ladder pool composition drill

(The former `future30yUpperN` and `future30yUpperAmdPerBondPerYear` straight-line fields are removed.)

### `laterMatIntContribution(qty, bond, refCPI)`

```
contribution = qty × 1,000 × indexRatio × bond.coupon
             = qty × annualInt   (where annualInt from bondCalcs)
```

What a processed rung adds to the running `laterMatInt` pool.

**Spec reference:** 4.0 Phase 4, step 4.

## allocation-policy.js

Within-year rebalance target/sell ordering. Formulas and policy definitions in **2.0 §Within-Year
Allocation Policy**; wiring into the per-year sweep in **3.0 §Target CUSIP resolution**. Pure
functions — no ladder state, no I/O; scoped to ordinary (non-bracket/gap/future30y) funded years
only, never called for a bracket/gap/cover year.

### `rankForYear({ candidates?, held?, piMap?, tipsMap?, policy?, rankOverride?, maturityPref? })`

**Inputs:**
- `candidates` — that year's canonical `yearTipsListMap[year]` entries (ladder-eligible TIPS,
  `maturityPref`/`yearOverrides`-driven — 2.0 §Maturity Selection Within a Funded Year).
- `held` — that year's currently-held holdings; may include maturities no longer in `candidates`.
- `piMap` — `{ cusip → piPerBond }` for every held cusip (used by `'equal'` to value each holding).
- `tipsMap` — used by `'saYield'` to look up each candidate's SA yield.
- `policy` — `'equal'` (default) | `'maturity'` | `'saYield'`.
- `rankOverride` — an explicit `cusip[]`, highest-priority-first (the per-year override); when
  present, used verbatim in place of the policy's own sort.
- `maturityPref` — `'last'` (default) | `'first'` | `'semiannual'` | `'all'` | `'select'`; only its
  direction (`'last'` vs `'first'`) matters here, as the tie-break for `'maturity'`/`'saYield'`.

**Returns:** an array of `{ cusip, held }`, over the union of `candidates` and `held`, highest
buy/hold-priority first. Never alters `held`'s own quantities — ranking decides order only (2.0
§Within-Year Allocation Policy, the "never manufactures a trade" invariant).

**`rankOverride`** — every override cusip present in the union is placed first, in the override's own
order; anything left over (a candidate/held cusip the override doesn't mention — e.g. a stale
override from before `maturityPref` changed) is appended afterward in candidate order, so a stale
override never silently drops a cusip from consideration.

**`dir` (maturity tie-break direction):** `dir = maturityPref === 'first' ? -1 : 1`. `+1` sorts
latest-maturing first (default, matches `'last'`'s own semantics); `-1` flips to earliest-first.
Applied to: the `'maturity'` policy's primary sort, `'saYield'`'s fallback sort when SA yield is
missing, and `'equal'`'s own tie-break when two candidates share the same held value.

**`'maturity'`:** `sort((a, b) => dir * (maturityOf(b) - maturityOf(a)))`.

**`'saYield'`:** sorts by `tipsMap.get(cusip).saYield` descending; a cusip with no SA yield never
outranks one that has a real value (`av == null → 1`, `bv == null → -1`); when both are missing,
falls back to the maturity-direction tie-break above.

**`'equal'`:** sorts ascending by currently-held value (`(heldByCusip.get(cusip)?.qty ?? 0) ×
(piMap[cusip] ?? 0)`) — a not-held candidate has value 0 and therefore ranks first (buy priority);
ties fall back to the maturity-direction tie-break. This ranking alone only decides *which single
CUSIP* is `rank[0]` for a given run — the actual value-leveling across the whole pool over the
course of a trade is `levelValues()`, below, not this sort.

### `levelValues(values, needed)`

**Inputs:** `values` — `Map<cusip, currentPIValue>`; `needed` — the pool's target total PI value
after the trade.

**Returns:** a new `Map<cusip, leveledPIValue>` summing to `needed`.

Growth (`needed > Σ values`) water-fills onto the currently-lowest value(s) in the pool; shrinkage
drains the currently-highest value(s); when two or more members are tied at the extreme being
adjusted, they move together for the remainder of that step. Implemented by iteratively merging the
pool into value-tied groups: at each step the extreme group's value is pushed toward the next-lowest
(growth) / next-highest (shrinkage) group's value — either exhausting the remaining delta partway
there, or reaching that group exactly and merging into it (repeat) — until the delta is exhausted or
only one group remains (the residual splits evenly across whatever's left in that final group).

**Why this exists (not a single-target drain).** `'maturity'`/`'saYield'` are fixed preference
orders, so draining the least-preferred CUSIP fully before touching the next is correct — there is
never a reason to touch a more-preferred CUSIP while a less-preferred one still has anything to give.
`'equal'` has no such fixed order: its whole point is to keep the pool's maturities near parity, so a
one-shot dump of a shrink/growth entirely onto whichever CUSIP ranked last at the *start* of the
trade can overshoot past parity and flip which CUSIP ends up larger — e.g. two maturities held 7 and
9 (by value), a shrink to a 12 total: draining only the 9-side down to 5 leaves it *below* the
untouched 7-side, the same magnitude of imbalance in the opposite direction. `levelValues` instead
brings both to 6/6 — parity, then an even split of anything beyond it.

## ladder-core.js — Shared ladder sizing pipeline

The single authoritative implementation of "size the target ladder from a DARA". **Both**
`build-lib` and `rebalance-lib` call `sizeLadder`; neither reimplements funded sizing, the
pre-ladder-interest (PLI) pool, gap/future-30Y duration matching, or the corrected sweep.
`rebalance-lib` also calls `sizeFuture30yCover` directly (see below) for its own pre-PLI pass —
it used to carry an inline duplicate of that formula, which had drifted out of sync with
`bracketWeights`' `[0,1]` clamp (KNOWN_ISSUES.md).

### `selectLadderBonds({ tipsMap, firstYear, lastYear, settlementDate, maturityPref?, couponPref?, yearOverrides? })`

Picks the canonical bond set purely from `tipsMap`: the funded-year TIPS list per year (via
`selectYearTips`/`maturityPref`/`couponPref` — see 2.0 §Maturity Selection Within a Funded Year),
the 2040 upper bracket, the active lower bracket (most recently issued 10-year TIPS below the gap), and the future-30Y cover pair (2056
lower, 2052 upper). Returns `{ yearBondMap, yearTipsListMap, rangeYears, gapYears, future30yYears,
future30yLowerYear, future30yUpperYear, future30yLowerCoverBond, future30yUpperCoverBond }`:

- `yearBondMap[year]` — the single representative TIPS (the latest of that year's list); every
  bracket/gap/cover path keys off this and is unaffected by `maturityPref`/`couponPref`.
- `yearTipsListMap[year]` — the ordered funded-year TIPS list (≥1) that `sizeLadder` sizes against.

This is the single source for "which TIPS the target ladder holds", so build and rebalance size
against an identical set. `couponPref` defaults to `'higher'`; only `runBuild` threads a caller
value through — `runRebalance`/`runFundedRebalance` never pass `couponPref`, so rebalance always
gets the default (see 2.0 §Maturity Selection Within a Funded Year, "Build-only today").

`yearOverrides` (Build only — 2.0 §Picking Maturities for a Funded Year): a `Map<year, cusip[]>`
naming an explicit TIPS list for that year, resolved against that year's candidates and sorted by
maturity; used in place of `selectYearTips(...)` for any year present in the map. An override whose
CUSIPs don't resolve to real candidates is ignored (falls back to the policy pick, so
`yearBondMap`/`gapYears`/`future30yYears` classification stays correct even for a year the picker's
"Select maturities" UI has forced to $0 DARA — see 2.0). Callers own the $0-DARA forcing themselves
(`index.html`'s `_runBuildFromForm`); `selectLadderBonds`/`sizeLadder` have no "unfunded year" concept
of their own beyond whatever `daraByYear` says.

### `sizeYearRungs(list, need, refCPI)` / `aggregateRungs(rungs)`

Splits one funded year's real P+I `need` evenly across its ordered TIPS `list` (from
`yearTipsListMap[year]`), each sub-rung sized from its own P+I; the latest maturity absorbs the
rounding remainder. `N = 1` reproduces the legacy single-TIPS sizing exactly. Returns
`[{ bond, ir, pi, coupon, qty }]` earliest→latest. `aggregateRungs` sums a sized rung list into
`{ qty, annualInterest, piTotal }` (total funded qty, total real annual coupon for LMI, total real
P+I delivered).

**Spec reference:** 2.0 §Multi-TIPS Funded-Year Split.

### `sizeFuture30yCover({ future30yYears, future30yLowerCoverBond, future30yUpperCoverBond, settlementDate, dara, daraByYear?, refCPI })`

The future-30Y half of duration matching (2.0 §Duration Matching (Brackets), §Future 30Y Rungs):
`future30yParamsCore` → cover durations → `bracketWeights` → `bracketExcessQtys`. Pulled out of
`sizeLadder` as its own function because `rebalance-lib` needs the cover excess quantity (for its
AMD pre-ladder pool) **before** the rest of `sizeLadder` runs — `sizeLadder` calls it too, so build
and rebalance run the identical, clamped duration match rather than rebalance carrying its own
copy of the formula. No-op (all-zero/null) when `future30yYears` is empty.

Returns `{ future30yParams, future30yLowerDuration, future30yUpperDuration, future30yLowerWeight,
future30yUpperWeight, future30yLowerExQty, future30yUpperExQty, future30yFellBack,
future30yTotalExcessCost, future30yLowerMonth, future30yUpperMonth }`.

`future30yParams` is `future30yParamsCore`'s own return: `{ avgDuration, future30yTotalCost,
breakdown, future30ySeedLMI, anchorBond }`. Unlike Gap years, every Future 30Y year is priced flat
off one bond — `anchorBond` (the 2056 lower cover) — rather than interpolated between two, so each
`breakdown` entry's `synYld` is the same `anchorBond.yield` for every year; `synCpn`/`durDetail` are
the same fields `gapParamsCore`'s breakdown carries, for the same Level-3 drill-down purpose (5.0
§Nested (Level-3) drills `f30dur-<year>`).

### `sizeLadder({ dara, daraByYear?, firstYear, lastYear, rangeYears, gapYears, future30yYears, yearBondMap, yearTipsListMap?, tipsMap, refCPI, settlementDate, settlementYear, preLadderInterest?, future30y cover bonds/years })`

Pure function: per-year DARA + bonds → target ladder. Runs, in maturity order: the prelim sweep
(PLI bucket + gap-LMI estimate, via `sizeYearRungs`/`aggregateRungs` when a year holds >1 TIPS),
future-30Y duration match + cover excess, the **AMD schedule** (held-to-maturity 2052 interest,
Option C), the **PLI pool** (zeroing + partial credit), gap duration match + bracket excess, then
the corrected long→short funded sweep. `yearTipsListMap` is optional — when omitted, each year
falls back to its single `yearBondMap[year]` TIPS (back-compat with pre-multi-TIPS callers).

Returns the target quantities and the params/pool fields callers render, including
`corrFYQty`, `corrRungs` (`{ [year]: rungs[] }` — the sized sub-rung list per year, from
`sizeYearRungs`; `build-lib.js` consumes this to emit one `results`/`details` row per sub-rung),
`zeroedFundedYears`, `partialCreditYear`, `partialCredit`, `pliCreditByGapYear`,
`pliCreditByFundedYear`, `gapParams`, and the future-30Y/AMD fields.

**Single-source consequence:** a build→rebalance round-trip (build's CUSIP/qty output fed back as
holdings, same DARA/firstYear/lastYear) produces **zero trades** and **zero net cash**. Rebalance
derives per-year DARA from the portfolio, calls `sizeLadder`, then diffs the result against current
holdings into buys/sells. Holdings never enter the sizing — only DARA does. Previously each
orchestrator hand-wrote its own PLI pool; they drifted at the partial-credit boundary year (2040),
which was the build↔rebalance symmetry bug.

**Adapters feed shared cores.** `ladder-core`'s `calcGapParams` (build's "LMI above gap" =
prelim coupon) and `rebalance-lib`'s `calculateGapParameters` (LMI from actual holdings + future
cover) are thin holdings/prelim adapters that both call the shared `gapParamsCore` in `gap-math.js`.
The gap sweep itself is defined once.

## Weighted Modified Duration

Both `build-lib.js` and `rebalance-lib.js` compute `weightedAvgDuration` (the portfolio weighted modified duration) and include it in the returned `summary`.

**Formula:**
```
weightedAvgDuration = Σ(mv_i × mDuration_i) / Σ(mv_i)
```

where:
- `mv_i = totQty_i × costPerBond_i` (build: `fundedYearQty + excessQty`; rebalance: `qtyAfter`, where for bracket rows `qtyAfter = fyQty + excessQtyAfter`)
- `mDuration_i = calculateMDuration(settlementDate, bond.maturity, bond.coupon, bond.yield)` from `shared/src/bond-math.js` — called with the same arguments as all other duration calls; no changes to that function
- Sum runs over all TIPS rows in `details`

**Implementation:** `mDuration` is computed per detail row during the details-building loop (while the bond maturity Date is in scope) and stored on the detail object. `weightedAvgDuration` is derived from the details array after the loop completes.

**Display:** `#wad-display` (label: `Avg Mod Dur`) and `#avg-yld-display` (label: `Avg Yld`) in `#ladder-stats-display` in Row 2 of the top card, shown after run in both modes. Modified duration has no unit suffix (dimensionless); yield is displayed as a percentage (e.g. `2.15%`). See 6.0 UI Layout §Row 2.

**`weightedAvgYield` formula:**
```
weightedAvgYield = Σ(mv_i × yield_i) / Σ(mv_i)
```
Same MV weights as `weightedAvgDuration`. `yield_i` is `d.yield` (real yield from market data, stored on each detail row). Included in `summary` from both `build-lib.js` and `rebalance-lib.js`.
