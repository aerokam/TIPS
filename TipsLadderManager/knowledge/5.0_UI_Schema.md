# 5.0 UI Schema

## Dependencies
**Requires:** 3.0 TIPS Ladder Rebalancing, 4.0 Computation Modules

**This file specifies the UI column schema, table rendering logic, and popup routing.**
It is the authoritative reference for `render.js` and `drill.js`.

---

## Purpose

A single `COLS` array drives all table rendering for both Rebalance and Build modes.
Adding, removing, or changing a column requires editing one object in `COLS` only —
headers, cell values, sub-row values, totals, and popup wiring all derive from it.

**Before-state on load (Rebalance):** Qty Before / Cost Before / Amount Before render as soon as
holdings load — before Rebalance Ladder is clicked. See 3.0 §Before-State Preview and Bracket-Year
Excess Detection for the computation and 6.0 §Before-State on Load for the layout/gating
consequences.

---

## COLS Schema

Each column is defined by one object:

```js
{
  label,        // string — header text and display label
  key,          // string — colKey used for popup routing and data binding
  fmt,          // 'str' | 'fy' | 'amt' | 'qty' | 'sgn' — formatting type
  rebalOnly,    // bool — column appears in Rebalance mode only (default false)
  buildOnly,    // bool — column appears in Build mode only (default false)
  fyLevel,      // bool — value is year-level, not per-TIPS (default false)
                //   group header: uses first row's value (not sum); null renders blank
                //   child TIPS rows: always blank (value is shown only in group header)
                //   excess sub-rows: unaffected (subValue still renders normally)
  value,        // fn(d, r) → number|string — main row cell value
  subValue,     // fn(d) → number|string | null — Gap sub-row cell value (bracket rows only)
  total,        // bool — include in totals row (default false)
  drill,        // bool — cell is drillable (clickable popup) (default false)
  drillCond,    // fn(v, d) → bool | null — override drill condition (default: v != null && v !== 0)
}
```

`render.js` filters `COLS` by mode before rendering:
```js
const activeCols = COLS.filter(c => mode === 'rebal' ? !c.buildOnly : !c.rebalOnly);
```

informational (2.0 §Within-Year Allocation Policy Part A), and also the input the SA-Yield-order
allocation policy ranks by, so unlike `yield` it renders in **both** modes (no `buildOnly`/`rebalOnly`
flag). Sourced from `TIPS/YieldsSaSao.csv` (`DATA_DICTIONARY.md#s10`), joined onto `tipsMap` by
CUSIP; a TIPS with no row in that file renders blank in this column (`fmtCell` on `null`, never a
fallback derivation) — the Mkt popup and drill-popup SA Yield fields instead show `—` for the same
missing-value case (`drill.js`, `index.html` `_showTipsRefModal`); the table column's blank rendering
is `fmtCell`'s generic null handling (shared by every `'yld'`/numeric column), not a deliberate choice
specific to `saYield`.

The `fundedYear` column has been removed from `COLS`. Funded year is now represented structurally as a **Group Header Row** (see §Funded Year Group Header Row below). `render.js` must no longer emit a funded-year `<td>` on any TIPS row.

**The "DARA / Maturity" label signals a conceptual dual role, not a literal joined string.** On TIPS child rows and excess sub-rows the cell shows the real maturity date/string exactly as today (`d.maturityStr`, unchanged, not editable) — the "Maturity" half of the label. On the funded-year group header row, there is no separate cell at the Maturity column's position at all (that position is part of the header row's single merged toggle cell, unchanged — §Funded Year Group Header Row §Structure); the DARA element renders inside that merged cell, next to the funded-year label. The header label conceptually covers both, but the `<th>` itself renders as a **two-row stacked header**, matching the CUSIP column's existing "Funded Year" (row 1) / "CUSIP" (row 2) stack (`render.js` COLS `cusip` entry's `headerHTML`): row 1 = "DARA", row 2 (smaller, dimmed) = "Maturity" — two separate lines aligned with "Funded Year" / "CUSIP" next to them, never a single "DARA / Maturity" joined string in the rendered `<th>`.

## Sub-Row Logic

For bracket and Future 30Y cover rows, a sub-row is rendered showing excess quantities. Sub-rows are labelled **"Gap"** for the 2037–2039 gap brackets and **"Future 30Y"** for the Future 30Y cover pair.

**Row ordering:**
- Gap lower bracket: main row first, Gap sub-row second
- Gap upper bracket: Gap sub-row first, main row second
- Future 30Y upper cover (e.g. 2052): main row first, Future 30Y sub-row second (same as lower bracket)
- Future 30Y lower cover (2056): main row first, Future 30Y sub-row second (same as lower bracket)

Both Future 30Y cover TIPS follow the lower-bracket pattern: excess sub-row always below the funded year row.

This ordering places gap coverage visually between the gap bracket rows, and Future 30Y coverage below each cover TIPS:
```
[gap lower bracket main]
[gap lower bracket — Gap sub-row]
... [non-bracket years] ...
[gap upper bracket — Gap sub-row]
[gap upper bracket main]
... [non-bracket years] ...
[Future 30Y upper cover main]   ← light blue
[Future 30Y upper cover — Future 30Y sub-row]  ← light yellow, label "Future 30Y"
... [years between Future 30Y upper and 2056] ...
[Future 30Y lower cover (2056) main]   ← light blue
[Future 30Y lower cover — Future 30Y sub-row]  ← light yellow, label "Future 30Y"
```

**Row identification:**
- Gap brackets: `d.excessQtyBefore > 0 || d.excessQtyAfter > 0` (rebalance) or `d.excessQty > 0` (build)
- Gap upper bracket: `d.fundedYear === summary.brackets.upperYear`
- Future 30Y cover TIPS: `d.fundedYear === summary.future30yUpperYear || d.fundedYear === summary.future30yLowerYear` when `summary.lastYear > 2056`

**Retained bracket excess:** each retained maturity also gets a Gap sub-row, inserted oldest-first between the active lower bracket's Gap sub-row and the non-bracket rebalance years. The count is not fixed — render one per retained maturity present.

**Color coding:**
- `tr.bracket:not(.excess-subrow)` → light blue — gap bracket main rows and Future 30Y cover main rows
- `tr.excess-subrow` → light yellow — all excess sub-rows (Gap and Future 30Y); label distinguishes them

**Spec reference:** 3.0 §Future Cover, 3.0 §Funded Year vs Excess (Bracket Years).

## Funded Year Group Header Row

`render.js` groups the `details` array by `fundedYear` and emits one `<tr class="fy-group-header">` immediately above each group's TIPS rows.

### Structure

```
[▼/▶] [fundedYear label]  [DARA]  [agg col 3]  ...  [agg col N]
       ↑ one merged label cell (colspan=labelCount — CUSIP + Maturity + SA Yield
         positions in Rebalance, + Yield in Build)
```

- **Toggle cell** (`colspan=labelCount`, where `labelCount` = count of `str`/`yld` columns, dynamically computed from the active, mode-filtered `COLS` — `cols.filter(c => c.fmt === 'str' || c.fmt === 'yld').length`, `render.js`): 3 in rebalance mode (CUSIP, Maturity, SA Yield), 4 in build mode (CUSIP, Maturity, Yield, SA Yield). Was 2/3 before SA Yield (§Shared columns above) added a second `'yld'` column to Rebalance. Contains the expand/collapse glyph (`▼` expanded, `▶` collapsed) and the funded year integer, followed by the DARA input (§DARA Input below) in the same cell's existing whitespace. Bracket years append `*` (e.g., `2036*`). Left-aligned.
- **Numeric cells**: one per active numeric column (every column except CUSIP, Maturity, Yield, and SA Yield). Shows the group aggregate; see §Aggregation rule below. Excess/sub-row values are **excluded** from the header; excess rows remain visible as child rows with their own values.
- Bracket-year header gets class `bracket` in addition to `fy-group-header`.

#### DARA Input

The funded-year group header row is the **only** input surface for per-year DARA, in both Rebalance
and Build (replaces the standalone Per-Year DARA Panel — 6.0 §Per-Year DARA (Table-Integrated)). A
compact editable number renders inside the same merged toggle cell described above, immediately
after the funded-year label (e.g. "▼ 2036  [DARA: 42,000]") — no separate cell, no column of its
own. The Maturity column's `<th>` header (top of table) changes from the single line "Maturity" to a
two-row stacked header, "DARA" (row 1) over "Maturity" (row 2, smaller, dimmed) — mirroring the
CUSIP column's existing "Funded Year" / "CUSIP" stack immediately to its left — to signal that this
is where the DARA value conceptually lives on header rows, even though structurally it's rendered
inside the toggle cell rather than in a cell at the Maturity column's position. On TIPS child rows
the Maturity column is unaffected — still its own cell showing `d.maturityStr`, not editable.

- **Store/mechanics unchanged.** The element reads from and commits to `_daraByYearStore` via the
  same `getDaraByYear()` / persistence mechanics as before (3.0 §Per-Year DARA (`daraByYear`),
  §Per-Rung DARA Selection, §Persisting a DARA plan across sessions) — only the input's location moved.
- **Applies to every funded year**, not just flagged bracket-candidate years — this is the general
  per-year DARA entry point. For a year flagged per 3.0 §Before-State Preview and Bracket-Year
  Excess Detection, entering a value here is also what resolves that year's flag (§Bracket-Year
  Excess Flag below).
- Gap years and Future 30Y years, which have no TIPS row of their own but still get a group header
  row, take their DARA input the same way.

#### RMD Options link

The settlement year's group header row — and only that row — additionally carries a plain "RMD
options" link (`.fy-rmd-link`), in the same merged toggle cell, immediately after the DARA input
(2.0 §RMD Options). No other year ever renders this link: the settlement year is structurally the
only funded year with both already-paid and not-yet-paid coupons in the same calendar year, so it's
the only row where the choice is ever meaningful. A trailing `*` on the link label
(`RMD options*`) marks a non-default choice, visible without opening the popover.

Clicking the link opens `#rmd-options-popover`, a single shared fixed-position popover (not a
per-row element, since at most one row ever shows the link) holding the cash-override number input
and the three-way coupon-mode radio group. Committing a value (`change` on the number input,
`change` on a radio) writes `_rmdCashOverride`/`_rmdCouponMode` and, matching the DARA input's own
commit rule, live-recomputes the pre-Run rebalance preview or an already-run Build; a post-run
Rebalance table only picks up the new value on the next Run. The link and popover are excluded from
the group header row's click-to-select/expand behavior (`.fy-rmd-link` alongside `.fy-dara-input`
and `td.drillable` in both the mousedown and click handlers) the same way those two already are.

The link itself carries `data-tip-html` — the same attribute the funded-year bracket label already
uses for its own hover explainer (§Funded Year Group Header Row above), so it's picked up by the
existing `mouseover`/`mouseout` delegation on `simpleEl`/`tableEl` and rendered in the same shared
`#bracket-tooltip` box with no separate hover mechanism or dedicated "?" affordance, matching how
the bracket label is both the content and the hover target. Hovering shows the explainer; clicking
still opens the popover — the two don't conflict, the same as any link that also carries a tooltip.

### Aggregation rule

Group header cell value depends on the column's `fyLevel` flag:

| Column type | `fyLevel` | Group header value |
|---|---|---|
| Year-level (`amtBefore`, `amtAfter`, `amount`) | `true` | First non-null value across groupRows; null (all rows null) renders as blank |
| Per-TIPS (`cost*`, `qty*`, `qtyDelta`, `cashDelta`, `cost`, `qty`) | `false` | `sum(col.value(d))` across all rows in group |

Year-level columns hold a single funded-year quantity (ARA Before/After, funded year amount). Summing would double-count when two TIPS share a funded year. The implementation scans groupRows for the first non-null value rather than always using `groupRows[0]`, because multi-TIPS funded years processed via reverse-loop + unshift may place a null-araBeforeTotal row first. If all rows are null (e.g., near-maturity TIPS), the header cell renders blank — not zero.

The `totalFn` (tfoot totals row) is unchanged — it still includes excess. Only the group header uses this narrower aggregate.

### Bracket-Year Excess Flag (Median Guess, Amber ⚠)

3.0 §Before-State Preview and Bracket-Year Excess Detection flags at most one lower-bracket
candidate (2032–2035, the one with the **highest excess** among those that exceed the held-year
median — not the latest-maturing one; matches the real engine's Excess ARA Priority rule) plus the
upper bracket (2040) and each Future 30Y cover (2052, 2056) independently, whenever a candidate's
raw ARA exceeds the held-year median. For a flagged year, the funded/excess split is not yet known
for certain, so a best guess is shown immediately rather than left blank:

- The flagged year's DARA input (§DARA Input above) is pre-filled with the held-year median, marked
  with the amber ⚠ "auto-set to median" indicator already used elsewhere in this app for auto-capped
  years (`_bracketAutoCapYears` / `_daraByYearRow`'s `bracketFlag` in `index.html`) — same tooltip
  language: "Auto-set to median: holdings suggest bracket excess. Adjust if this year is intended
  for higher income."
- `amtBefore`'s group header value (fyLevel, this Aggregation rule) is the pre-filled median for that
  year; the year's Gap sub-row shows the resulting excess, `raw ARA − median` — rendered immediately,
  not withheld pending user input.
- `qtyBefore` / `costBefore` group header values ARE affected for a flagged year (unlike every other
  year, where they're untouched by the funded/excess split): 3.0 §Before-State Preview's "Qty Before
  / Cost Before split for a flagged year" — `fundedYearQtyBefore = round((DARA − LMI) / piPerBond)`,
  `fundedYearCostBefore = fundedYearQtyBefore × costPerBond`, with the remainder
  (`heldQty − fundedYearQtyBefore`, floored at 0) and its cost shown on the Gap sub-row alongside the
  excess Amount — so the funded row and Gap sub-row read as one internally consistent split, not a
  large undivided qty/cost next to a small Amount.
- If the user edits the flagged year's DARA input, the ⚠ clears and `amtBefore`, `qtyBefore`,
  `costBefore` (group header and Gap sub-row alike) all recalculate live against the entered value
  (still the same LMI-based formula, not duration-matched, whether the value is the median guess or
  user-entered).

This is a **preview-only** display rule — it does not change what Rebalance Ladder computes (3.0
§Before-State Preview and Bracket-Year Excess Detection, "Scope: preview only").

### Child rows

All TIPS rows belonging to the group are emitted after the header with class `fy-child`. Excess sub-rows (`.excess-subrow`) are also `fy-child` rows — they are children of the same group and collapse/expand with it.

**`fyLevel` columns on child rows:** `amtBefore`, `amtAfter`, and `amount` render as blank `<td></td>` on all main TIPS child rows. The value is already shown in the group header. Excess sub-rows are unaffected — their `subValue` (excess dollar amount) still renders normally.

```html
<tr class="fy-group-header [bracket]" data-fy="2036" data-expanded="true">…</tr>
<tr class="fy-child bracket" data-ri="…">…</tr>          <!-- TIPS main row -->
<tr class="fy-child excess-subrow bracket" data-ri="…" data-sub="1">…</tr>  <!-- excess -->
```

### Expand/collapse behaviour

- **Default:** all groups expanded (`data-expanded="true"`).
- **Click on header row:** toggles `data-expanded` between `"true"` and `"false"`. All `.fy-child` rows with matching `data-fy` get `hidden` attribute set/cleared. **Exception:** if the clicked cell has class `drillable`, the click is treated as a drill action and does NOT toggle expand/collapse.
- **Expand All / Collapse All buttons:** set all group headers to the target state and show/hide all child rows accordingly.
- Expand/Collapse All buttons are placed in the form-card actions row (see 6.0 §Collapsible Groups).

### Drillable cells in group header rows

`fyLevel` columns that have `drill: true` emit a drillable cell in the group header row. The implementation finds the first non-null row in the group (along with its `ri`), checks `drillCond(value, d)`, and if true renders:

```html
<td class="drillable" data-row="<ri>" data-col="<colKey>" style="text-align:right">…</td>
```

The `data-row` attribute points to the `details[]` index for the non-null row, so the global drill click handler (`document.addEventListener('click', …)`) can route to the correct popup exactly as it does for child-row drillable cells. When all rows in the group have a null value for the column, no drillable cell is emitted (blank `<td>` instead).

### CSS classes summary

| Class | Applied to | Meaning |
|---|---|---|
| `fy-group-header` | `<tr>` | Funded year group header row |
| `fy-child` | `<tr>` | TIPS row or excess sub-row inside an expanded group |
| `fy-group-header.bracket` | `<tr>` | Group header for a bracket year |
| `drillable` | `<td>` | Cell that opens a drill popup on click; may appear in group header rows (fyLevel cols) or child rows |

**Spec reference:** 6.0 §Collapsible Groups for visual styling.

### Duration Disclosure Standards

Both **Duration Calcs** and **Future 30Y Duration Calcs** popups must follow a consistent, transparent structure:

1.  **Block Average**: Display the Average Duration of the missing block (Gap or Future 30Y) at the top.
2.  **Hypothetical Breakdown**: List every synthetic/hypothetical bond in the block with:
    *   Maturity Year and assumed date (e.g., "2037 (Jan 15)" or "2058 (Feb 15)").
    *   Individual Modified Duration, drillable into its full derivation (§Nested (Level-3) drills
        `gapdur-<year>`/`f30dur-<year>` above).
3.  **Average Derivation**: Explicitly show the mean calculation (Sum / Count).
4.  **Bracket/Cover Pair**: List the existing TIPS used for coverage and their Modified Durations.
5.  **Weight Solver**: Show the weights derived from the matching formula.
6.  **Fulcrum Visualization**: Display the `renderDurationBeam` visual.

**Why yield is interpolated, not duration.** Each synthetic bond's yield is interpolated from real
anchor bonds, then its coupon is reconstructed from that yield (`syntheticCoupon`, mirroring how
Treasury sets a new issue's coupon ≈ prevailing yield), and only then is duration computed from
`{maturity, coupon, yield}` via `calculateDurationDetail` — the same function every other duration in
this app goes through. Interpolating duration directly between the two anchor bonds' own durations
was considered and rejected: those bonds carry whatever coupon was set at their own auction, not an
at-the-money coupon for today's curve, so a duration blended from their two durations would carry
their coupons' divergence from at-the-money as unexplained noise, and it would be a second duration
methodology existing alongside `calculateDurationDetail` rather than one method used everywhere.

**Note**: Quantity breakdowns for individual hypothetical bonds must NOT be shown in the Future 30Y Duration popup, as they do not represent actual holdings.

## Totals Row

Only columns with `total: true` show values in the totals row. Others show blank.

## Trade Ticket

A separate modal (`#trade-ticket-overlay`/`#trade-ticket-modal` in `index.html`), triggered by the
`Trade Ticket` button in Row 2 (6.0 §Form Card Layout). Not COLS-driven — built directly from
`buildDetails`/`rebalDetails` by `buildTradeTicketHTML(mode)`, independent of the main table.
Draggable/resizable (6.0 §Modal Frame Standard).

**Scope:** Build shows the full purchase list (`fundedYearQty + excessQty` per CUSIP, qty > 0).
Rebalance splits into **Buys** and **Sells** sections (`qtyAfter − qtyBefore` per CUSIP, sign
determines section); named "Trade Ticket" rather than "Purchase List" because Rebalance's list is
buys *and* sells, not purchases only.

**Columns:** CUSIP, Maturity, Qty, Cost, Accrued Interest, **Total Cost** (Build and Buys) /
**Total Proceeds** (Sells — identical formula, proceeds framing). Each row's Qty is always
positive; Sells price off `Math.abs(delta)` so Cost/Accrued/Total read as positive proceeds.

```
cost              = qty × costPerBond                                    // 2.1 §Cost per TIPS
accruedPerBond    = accruedInterest(coupon, ttSettlementDate, bond.maturity).accrued  // 1.0 §Accrued Interest, 4.0 §accruedInterest (nominal)
                    / 100 × indexRatio × 1,000                           // 2.1 §Accrued Interest (adjusted extension)
accruedInterest   = qty × accruedPerBond
totalCost         = cost + accruedInterest
```

`ttSettlementDate` = `localDate(activeRefCpiDateStr ?? _defaultRefCpiDateStr)` — the same forward-looking
"Settlement Date" (§RefCPI Date Override) used everywhere else in the app for `indexRatio`, not the raw
`settlementDate` global (which is the FedInvest pricing file's own settlement date, one bond-trading-day
behind: it reflects T+1 from the file's last-close data, not T+1 from today). A live order placed today
settles on the next bond trading day from today, i.e. `_defaultRefCpiDateStr`; using the stale `settlementDate`
for the day-count (A/E) understated Accrued Interest by about a day's accrual relative to a real broker
trade ticket, while `indexRatio` in the same formula already used the correct forward date — an internal
inconsistency. Fixed 2026-07-24.

`bond.maturity` (a Date, needed for the day-count calc) is resolved from the global `tipsMap` by
CUSIP — the detail row itself carries `maturityStr` (formatted), not a Date.

**Naming:** the Cost column is deliberately **not** called "Adjusted Price" or "Principal".
"Principal" already denotes the inflation-adjusted *face* value elsewhere in this app —
2.1 TIPS Basics §Par Value (Adjusted Principal) (`principalPerBond` = 1,000 × index ratio) — a
different, market-price-independent number from what a buyer actually pays. "Cost" matches the
main table's existing `Cost` / `Cost Before` / `Cost After` columns and "Cost per TIPS" popup
wording (§Popup Routing above) — reused rather than reinvented.

**Popup routing:** cells carry `class="tt-drill" data-tt-idx data-tt-key`, routed by a dedicated
click handler in `index.html` (separate from the main table's `td.drillable` handler) via
`showPopup` (`popup.js`), not the `#drill-overlay`/`buildDrillHTML` mechanism used by the main
table:

| `data-tt-key` | Builder (`drill.js`) | Content |
|---|---|---|
| `cost` | `buildTradeTicketCostDrill` | Price → Index Ratio → Cost per TIPS → Quantity → Cost |
| `accrued` | `buildTradeTicketAccruedDrill` | A → E → Coupon÷2 → Accrued Interest per TIPS → Quantity → Accrued Interest |
| `total` | `buildTradeTicketTotalDrill` | Cost → Accrued Interest → Total Cost / Total Proceeds |

**Spec reference:** 1.0 Bond Basics §Accrued Interest (nominal day-count); 2.1 TIPS Basics §Cost per TIPS, §Accrued Interest (index-ratio extension); 4.0 §accruedInterest.

## Cash Flow Calendar

A separate modal (`#cash-flow-overlay`/`#cash-flow-modal` in `index.html`), triggered by the **Cash
Flow** button in Row 2 (6.0 §Row 2). Answers a different question than the rest of the app: not "how
does this year's DARA get funded" but "when does my current portfolio actually pay me, and how much."
Independent of funded years, DARA, brackets, gaps, and Future 30Y covers — it is a fact about
`currentHoldingsArray` (every held CUSIP and its quantity), not a ladder-construction result, so it is
available as soon as holdings are loaded, before Run (6.0 §Row 2). Draggable/resizable (6.0 §Modal
Frame Standard) — the calendar can run 30+ years deep, so resizing taller is expected to be common.

**Scope:** actual held TIPS only — no synthetic gap-year or Future 30Y placeholders, since those are
not real cash flows.

**Ref CPI: each payment date's own Ref CPI where published, the active Ref CPI date's otherwise.** The
Ref CPI series (`refCpiRows`) is published roughly 2 months ahead of the active Ref CPI date (3.0
§RefCPI Date Override), so the first several payment dates in the calendar usually already have their
own published Ref CPI. Every payment date checks `lookupRefCpi(refCpiRows, thatDate)` first:
- **Published for that date (the common case for near-dated payments):** use it. This is the exception
  to how every other Amount figure in this app is priced, and is flagged as such in the drill-down
  (§Structure below) — `isActual: true`.
- **Not yet published (every other payment):** use the active Ref CPI date's value instead —
  `lookupRefCpi(refCpiRows, activeRefCpiDateStr ?? _defaultRefCpiDateStr)` — matching every other
  Amount figure in this app (5.0 §Trade Ticket "Naming"). The active Ref CPI date is the settlement
  date by default, or a date the user overrode (3.0 §RefCPI Date Override) — this is never "today":
  popup copy must name the actual date in play rather than assume one.

**Cutoff: today, not the settlement/Ref CPI date — and a coupon stays listed until it is actually
paid.** The rest of the app prices off the settlement date (`activeRefCpiDateStr ?? _defaultRefCpiDateStr`,
5.0 §Trade Ticket) because it is answering "what would a trade settle at." This calendar is answering
"has my portfolio paid me yet," so it walks from today (`_tradeDateStr`) instead. A coupon dated on a
weekend or bond holiday is actually paid on the next bond trading day (`nextBondTradingDay`,
`src/data.js`), so the event must remain on the calendar — still counted as unpaid — through that day,
even though its raw coupon date has already passed.

### Computation

```
today            = localDate(_tradeDateStr)                                  // start of the coupon walk — "has this been paid yet," not the trade-settlement date used elsewhere (5.0 §Trade Ticket)
walkFrom         = today − 10 days                                           // buffer so couponSchedule's forward walk doesn't miss a coupon delayed by a holiday weekend
dates            = couponSchedule(walkFrom, bond.maturity)                   // shared/src/bond-math.js — every coupon date from `walkFrom` through maturity inclusive
                     .filter(d => actualPaymentDate(d) >= today)             // drop anything already paid
// actualPaymentDate(d): d itself if d is a bond trading day, else nextBondTradingDay(d) — the weekend/holiday roll-forward
// per date d in dates:
actualRc         = lookupRefCpi(refCpiRows, isoDate(d))                      // that date's own published Ref CPI, or null
eventRc          = actualRc ?? lookupRefCpi(refCpiRows, activeRefCpiDateStr ?? _defaultRefCpiDateStr)
principalPerBond = bondCalcs(bond, eventRc).principalPerBond                 // 2.1 TIPS Basics §Par Value (Adjusted Principal)
couponPerBond    = principalPerBond × bond.coupon ÷ 2                        // one semiannual payment
```

For each held CUSIP, one coupon event is emitted per date in `dates` (amount = `couponPerBond × qty`),
each priced off that date's own `eventRc` — not one shared Ref CPI for the whole calendar. The final
date in `dates` always equals `bond.maturity`; that date additionally gets a principal event (amount =
`principalPerBond × qty`) — TIPS pay their last coupon and principal on the same day.
`couponSchedule` reuses the same coupon-date walk (`_nextCouponOnOrAfter` + semiannual stepping) that
`calculateDuration`/`yieldFromPrice`/`priceFromYield` already use, so a held TIPS's payment dates here
always agree with its duration/yield calculations elsewhere in the app.

**Staleness:** `_clearOutput()` closes the Cash Flow overlay and calls `hidePopup()` whenever the
active Ref CPI date changes (Apply or Reset in the RefCPI picker). Cash Flow's event list is computed
once per open, not live-bound to `activeRefCpiDateStr` — without this, changing the Ref CPI date while
the modal or its drill popup was open left the old date's figures on screen even after the date was
changed back.

### Structure: 4-level drill

Mirrors the funded-year group-header collapsible pattern (§Funded Year Group Header Row) rather than
introducing a new interaction model:

1. **Year rows** — one collapsible row per calendar year present in the event list, showing that
   year's Coupon / Principal / Total. The current year is expanded by default; every other year starts
   collapsed. Clicking a year row toggles its date rows' `hidden` attribute (no popup).
2. **Date rows** (children of an expanded year) — one row per distinct payment date in that year,
   showing the date's Coupon / Principal / Total.
3. **Level-3 popup** (click a date cell) — `buildCashFlowDateDrill` (`drill.js`) — reuses `showPopup`
   (`popup.js`) directly with a plain row-descriptor array, the same mechanism as the Trade Ticket
   drill popups, not the colKey-routed `buildDrillHTML` used by the main table. Ref CPI is a single
   national series, not per-bond, so every event sharing a date shares the same `refCPI`/`isActual`
   (§Computation above) — shown **once**, at the top, rather than repeated per line:
   - **Label row** — `refCpiDateDisplay` as the value; label is `"Cpn Ref CPI date"` when `isActual`
     (that date's own date), or plain `"Ref CPI date"` otherwise (the active Ref CPI date) — the label
     itself flags the exception, no separate explanatory sentence.
   - **Ref CPI** — the numeric value used for every line below.
   - Then one line per CUSIP event (`<CUSIP> — Coupon` / `<CUSIP> — Principal`, its amount, rendered as
     a clickable `.cf-event-drill` span), followed by the date's total.
4. **Level-4 popup** (click a `.cf-event-drill` line) — `buildCashFlowEventDrill` (`drill.js`) shows
   how that one CUSIP's payment was calculated: Ref CPI → Dated Ref CPI → Index ratio → Par Value per
   TIPS → (Coupon per period, for coupon events) → Coupon/Principal per TIPS → Quantity → Amount.
   Starts from the same Ref CPI value already shown at the top of Level-3 — nothing about which date
   it came from is repeated here. Routed via a `document`-level delegated click listener (matches the
   main table's `.drill-l3` nested-drill pattern, 5.0 §Nested (Level-3) drills) since the Level-3 popup
   is the body-level `#shared-popup` singleton, not a child of `#cash-flow-content`. Each event carries
   its own calc inputs (`qty`, `refCPI`, `baseCpi`, `indexRatio`, `principalPerBond`, `coupon`,
   `isActual`, `refCpiDateDisplay`) captured at `buildCashFlowData()` time, so this popup needs no
   re-lookup against `tipsMap` or `refCpiRows`.

### CSV Export

`#cash-flow-export` downloads the **full, flat, multi-year** event list regardless of which years are
expanded/collapsed in the modal — `Date,CUSIP,Type,Amount`, one row per coupon or principal event,
chronological. Same Blob/anchor-download pattern as Export CSV / Export CUSIP-Qty / DARA plan export.
