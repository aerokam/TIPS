## Form Card Layout

Three stacked rows inside `.form-card`:

### Row 1 — Inputs (`.card-inputs`)
Flexbox, `gap: 8px 20px`, `align-items: flex-end`.  
Contains: Holdings CSV, DARA, First Year (mode-dep), Last Year (mode-dep), Brackets (`#bracket-mode`,
rebalance-only — 2-bracket/3-bracket, with its own "?" help button), Pre-ladder int.

**Maturity preference, Allocation policy, and Coupon pick are not in Row 1** — they live in the DARA
Plan card's always-visible header row instead (§DARA Plan Card below), shared between both modes
rather than build-only. Moved there when Row 1 grew to nine field slots and users stopped noticing
the Allocation policy control existed; see that section for their current layout and the "Select
maturities"/"Set priority order…" modal-launcher behavior.

No yield-source control is exposed here — the card is already crowded, especially in Build mode. The market-data source is a single hardcoded constant (`YIELD_SOURCE` in `index.html`) rather than a user-facing choice; see 3.1 §4.0 Yield Sources.

### Row 2 — Run + Post-Run Actions (`.card-inputs`, `margin-top: 8px`)
Contains, in order: **Run button first** (`#run-btn`, "Rebalance Ladder"/"Build Ladder" depending on
mode — deliberately the first item of Row 2, not the last item of Row 1: it's always visible, just
disabled pre-load, unlike everything after it which stays `display:none` until a run happens), then
Export CSV, Export CUSIP/Qty, Trade Ticket (opens the cost-breakdown modal, see 5.0 §Trade Ticket),
and Duration links — every one of these last four `display:none` until a run completes.  
All items `align-self: flex-end`.

**Duration link button labels:** `Gap Dur` (gap/bracket duration calcs popup), `Future 30Y Dur`.

### Row 3 — Post-Run Stats (`#ladder-stats-display`, `margin-top: 4px`)
A row-flex container (`flex-direction:row; gap:16px; align-items:center`) holding four stats side by
side, shown after run (both modes). Hidden (`display:none`) until a result is available; shown as
`display:flex`.

- **`#avg-yld-display`**: `Avg Yld <value>%` — portfolio weighted average yield (%).
- **`#avg-sa-yld-display`**: `Avg SA Yld <value>%` — portfolio weighted average SA yield (%; 4.0
  §Weighted Modified Duration `weightedAvgSaYield`, same market-value weights as Avg Yld/Avg Mod
  Dur — 2.0 §Within-Year Allocation Policy Part A).
- **`#wad-display`**: `Avg Mod Dur <value>` — portfolio weighted modified duration (dimensionless;
  no unit suffix).
- **`#net-cash-inline`**: Net Cash (rebalance) / Total Cost (build) label + value.

All four use `.info-stat` / `.info-stat-val` styling (Net Cash/Total Cost additionally uses
`.nc-label`/`.nc-val`, §Row 4 typography table below).

### Row 4 — Info Strip (`.card-info`)
Single flex row, `gap: 12px`, `align-items: center`, `margin-top: 6px`, `padding-top: 6px`, `border-top: 1px solid rgba(255,255,255,0.12)`.

## DARA Plan Card

### Purpose

The DARA Plan card (`#dara-plan-card`) holds two kinds of controls:

- **Always-visible header row** (`#dara-plan-hdr-row`, `.card-inputs`) — a static "DARA Plan" label +
  Show/Hide Details toggle button, and the Maturity preference / Allocation policy / Coupon pick
  fields (2.0 §Maturity Selection Within a Funded Year, §Within-Year Allocation Policy) — shared
  between Rebalance and Build, live regardless of whether a DARA plan exists yet.
- **Collapsible body** (`#dara-plan-body`) — the plan-level controls that act on the whole per-year
  DARA shape rather than a single year: split-year chips + add-select, each segment's row (label,
  **Infer DARA** button in rebalance, the **$ each** constant-stamp input), Undo/Revert, and the Save
  DARA Plan / Export / Import controls (3.0 §Segmented DARA, §Persisting a DARA plan across
  sessions). Only meaningful once a DARA plan exists, so it stays collapsed until opened.

These outgrew being a minor sub-panel — they're integral ladder-management controls, not an appendix
to the raw per-year table — so the card gets the **same visual weight as the main form card**
(`.dara-plan-card`: same background/border/shadow as `.form-card`, but a normal `border-radius: 8px`
on all corners since it isn't flush against the tab bar).

`#dara-plan-body`'s children are ordered by how often each one needs to be seen and acted on, most-urgent first: the saved-plan-found Apply/Dismiss banner (`#dara-plan-banner`) leads, since an unactioned saved plan is the thing most likely to need a decision the moment the body opens; then Undo/Revert (`#dara-history-tools`); then the Save row (`#dara-remember-row`: the Save DARA Plan button, the "✓ Saved" flash, and the "⋮" menu holding Export/Import — 3.0 §Standalone DARA-plan file); then the split-year/segment tools (`#dara-seg-tools`, §Split-Years and Segment Rows below). Export/Import are tucked behind the "⋮" menu rather than shown as their own buttons — Save (localStorage, same device) covers the common case, and the two-click file-based path is for the less-frequent cross-device/cross-browser case.

### Header row

`#dara-plan-hdr-row` is a `.card-inputs` flex row of four `.field` blocks, always rendered (never
gated behind DARA-plan availability — only the body below it is):

1. **`#field-dara-plan-toggle`** — a static `<label id="dara-plan-hdr">DARA Plan<span
   class="badge-dot">` (not clickable — unlike the pre-this-feature sliver, the label is now inert
   text) plus `#dara-plan-toggle-btn`, a real `.plan-btn` reading `▶ Show Details` / `▼ Hide Details`
   (glyph + label both live in the button's own `innerHTML`, swapped by `_setDaraPlanOpen()`). A
   separate button exists here — rather than the whole row toggling on click, as the pre-this-feature
   sliver did — because the row now also holds three live form controls (below); a click-to-toggle on
   the entire row would need a `stopPropagation` guard on every one of them to keep those controls
   usable.
2. **`#field-build-maturity`** — Maturity preference (`#build-maturity`), shared with Row 1's old
   position, now living here instead (§Row 1 above).
3. **`#field-alloc-policy`** — Allocation policy (`#rebal-alloc-policy` + its "?" help button),
   Rebalance-only (`display:none` in Build — no held-vs-preferred distinction to order there). Its "?"
   popup enumerates all three policies plus "Set priority order…" (2.0 §Within-Year Allocation
   Policy). **Disabled and forced to "Maturity order"** whenever Maturity preference is "Last to
   mature"/"First to mature" (`.field select:disabled { opacity:.55; cursor:not-allowed }`); live
   otherwise (2.0 §Within-Year Allocation Policy).
4. **`#field-build-coupon`** — Coupon pick, `display:none` unless Maturity preference is not "Last to
   mature" (unchanged condition from when this lived in Row 1 — see 2.0 §Maturity Selection Within a
   Funded Year for why `'last'` never needs it).

Toggling `#dara-plan-toggle-btn` expands/collapses `#dara-plan-body`, tracked by `_daraPlanOpen` and
set via `_setDaraPlanOpen()` — closed by default, so a plain flat-DARA ladder that never touches
segments/Save/history never shows more than the header row. `_updateDaraRememberUI` also calls
`_setDaraPlanOpen(true)` when a saved plan is found for the current cache key — since a passive
dismissible banner alone was easy to scroll past. A badge dot (`.needs-attention` on `#dara-plan-hdr`,
driven by `_daraPlanNeedsAttention`) persists even if the user collapses the body again without
clicking Apply/Dismiss, so the found-a-saved-plan state can't be silently lost; cleared by the Apply
and Dismiss handlers.

### Placement and visibility

A dropdown, not a static block: `#dara-plan-card` is a normal-flow DOM child of `#top-row` (the
sticky main-card container). It pushes the ladder output table (`#output` / `#build-output`) below
it down when open — same push-layout behavior described below — rather than overlaying it; an
earlier `position: absolute` overlay version blocked clicks on the table underneath, which broke the
normal workflow of editing per-year rungs while the plan tools are open. Being a child of `#top-row`
(`position: sticky`) is what keeps it from scrolling away independently: the sticky row just
grows/shrinks in place as the dropdown opens/closes.

**Note (table-integrated DARA):** this section predates the removal of the standalone Per-Year DARA
panel (§Per-Year DARA (Table-Integrated) below) — per-year DARA is now entered inline in the ladder
output table's group header rows, not in a separate panel below this card. The card now sits
directly above that output table rather than above a dedicated DARA panel.

**Availability now gates only the collapsible body, not the whole card.** `_setDaraPlanAvailable()`
tracks the same condition that used to gate the entire standalone panel (valid DARA + range, holdings
loaded in rebalance) — but the header row's fields don't depend on a DARA plan existing at all
(Maturity preference/Allocation policy/Coupon pick are meaningful before any DARA has been entered),
so "unavailable" now only means the collapsible body (`#dara-plan-body`) can't be opened; the card and
its header row stay visible and interactive regardless.

A second, separate signal covers the opposite direction — an unsaved edit rather than an unactioned
saved plan. Any per-year value change (per-rung edit, segment Infer/`$ each`, the flat `#dara`
field, Undo, Revert) calls `_setDaraPlanDirty(true)` (3.0 §Persisting a DARA plan across sessions),
which also auto-opens the card via `_setDaraPlanOpen(true)` if collapsed, and rings
`#dara-remember-btn` (`.needs-save`, see Styling) rather than the header badge dot — the two states
are deliberately distinct (a header-level "something needs a decision" vs. a button-level "click
this one control"), so they never overwrite each other's indicator. Cleared by Save or Apply.

### Styling

Buttons, chips, inputs, and selects inside `.dara-plan-card` use the same teal-card token set as the main card's own controls (`.plan-btn` ≈ secondary button on `--portal-header-bg`, including the Save DARA Plan button itself and the "⋮" more-menu toggle (`#dara-plan-more-btn`); `.plan-chip` for split-year chips; `.plan-banner` for the saved-plan-found Apply/Dismiss banner) rather than the light-background styling still used by the plain Per-Year DARA table box below it. `.plan-btn.needs-save` (a red outline ring, `box-shadow: 0 0 0 2px #e05252`) highlights `#dara-remember-btn` while `_daraPlanDirty` is true; `.plan-banner` carries the same ring permanently (not conditional — the banner only renders while there's an unactioned saved plan, so it doesn't need its own toggle state) so the two "this needs a click" moments in the card read as visually related. The "⋮" menu toggle (`#dara-plan-more-btn`) sits directly beside `#dara-remember-btn` in its own tight-gap (`4px`) sub-row, separate from the row's normal `12px` gap to the "✓ Saved" flash and file input — close enough to read as "Save's options," not a free-floating control. The menu itself (`#dara-plan-more-menu`) is a small absolutely-positioned dropdown anchored under the toggle, holding the Export/Import buttons; it opens on click and closes on an outside click or on either button firing its action.

### Split-Years and Segment Rows

`#dara-seg-tools` (inside `#dara-plan-body`, 3.0 §UI: segment actions) is a two-part flex row
(`display:flex; align-items:flex-start; gap:16px; flex-wrap:wrap`):

- **Left, fixed width** (`flex-shrink:0`) — "Split years:" label, the split-year chips
  (`#split-year-chips`), the add-select (`#split-year-add`, "+ add split year"), and the "?" help
  button.
- **Right** (`#seg-rows`) — one `.seg-row` per resulting segment (3.0 §Segmented DARA `_segments()`),
  each a horizontal row of its own (bold year-range label, **Infer DARA** button in
  Rebalance, **$ each** input — `.dara-plan-card .seg-row { display:flex; align-items:center;
  gap:6px; margin-bottom:5px; flex-wrap:wrap }`). With no split years, `#seg-rows` holds exactly one
  such row, labelled "Whole ladder `<firstYear>`–`<lastYear>`"; with N split years it holds N+1,
  each labelled just its own year range (`<firstYear>`–`<lastYear>`, no "Segment" prefix — the split
  chips to the left already establish that segments exist, so the word is redundant and costs
  horizontal space).

`#seg-rows`'s children are ordinary block-level `.seg-row` divs, so multiple segments stack
vertically on their own lines — positioned to the **right** of the left cluster (not pushed onto a
new full-width line below it), so the two parts share the row's open horizontal space rather than
each claiming the full card width.

### Priority-Order Picker

`#rank-picker-overlay` / `#rank-picker-modal` — the per-year override modal for 2.0 §Within-Year
Allocation Policy's Part D, opened via the Allocation policy dropdown's "Set priority order…" choice
(same mousedown/change/click relabeling pattern as the Select-maturities picker, §Row 1 above,
duplicated for `#rebal-alloc-policy`). Structurally parallel to the maturity picker: same
draggable/resizable modal frame (`makeDraggableResizable`, `src/modal.js`), same close/cancel/apply
button row.

**One modal covers every year in range**, not a per-year launcher — an earlier revision added a
small icon next to each funded year's inline DARA input to open this modal pre-scrolled to that year;
it was removed once the Allocation policy dropdown became the single obvious entry point, since every
icon opened the identical whole-ladder modal (redundant once there's one clear home for "priority
order").

Each year renders as a row of **chips** — one per candidate/held CUSIP, current-priority order —
with **◀ / ▶** buttons on each chip to reorder (not ▲/▼: the chips lay out horizontally, so
left/right matches the actual direction a reorder click moves a chip; an earlier version used ▲/▼ and
was corrected). `#rank-picker-desc` states the convention: "Left = preferred to hold/buy first. Right
= sold first if this year needs to shrink." — plus a note that under Equal split a not-held maturity
can rank ahead of a held one (2.0 §Within-Year Allocation Policy), so that isn't a bug when seen in
the picker. A year left untouched follows whatever the global policy currently produces for it
(`rankForYear`, seeded via `_rankPickerYearOrder`) — opening and Applying with no edits is a no-op.
Apply writes to `_yearRankOverrides`; picking a different named global policy clears every override
(2.0 §Within-Year Allocation Policy).

## Per-Year DARA (Table-Integrated)

### Removal of the standalone panel

The standalone Per-Year DARA panel (`#dara-by-year`) described in earlier revisions of this spec is
**removed as a separate UI element**, in both Rebalance and Build. Its input surface moves into the
ladder output table itself — a compact editable DARA element in each funded-year group header row,
next to the funded-year integer, occupying the Maturity column's cell position (5.0 §Funded Year
Group Header Row §DARA Input; the Maturity column header text also changes to "DARA / Maturity",
5.0 §Shared columns).

**What is unchanged.** The underlying store/persistence mechanics are untouched by this move —
`_daraByYearStore`, `getDaraByYear()`, the DARA Plan card's split-year/segment/Infer/Undo/Revert
controls, the localStorage cache ("Save DARA Plan" button), and the standalone DARA-plan file
import/export (now reached via the "⋮" menu, see Styling above) all continue to exist exactly as
specified (3.0 §Per-Year DARA (`daraByYear`), §Segmented DARA, §Persisting a DARA plan across
sessions) — only the **input surface** moved out of a dedicated panel.

### Persistence rule (unchanged)

**User-modified values are authoritative and must survive re-renders.** Specifically:
- Every year the user edits is stored in `_daraByYearStore` (a `Map<fundedYear, number>`).
- `_daraByYearStore` is the source of truth for modified years. The DOM input values are a view.
- `getDaraByYear()` must consult `_daraByYearStore` first for each year; only fall back to the DOM
  input value for years not yet in the store.

### DARA field display (unchanged)

- When any stored year value differs from `_daraByYearPanelDefault`, the main `#dara` field shows
  **by year** (purple weight) instead of a numeric value.
- The underlying default (`_daraByYearPanelDefault`) is preserved in memory so `_getDefaultDara()`
  can return it while the field shows **by year**.
- Clicking ▲/▼ step buttons updates `_daraByYearPanelDefault` and overwrites **all** store entries
  to the new step value — the intent is to set all years uniformly.
- **`updateDaraInput(force)` overwrites a non-empty field too when `force` is true**, not just when
  it's empty. The un-forced path only fills a blank field (so it never clobbers a number the user is
  actively typing) and otherwise leaves whatever text is already there alone — correct while the user
  types, but wrong for a programmatic restore (Apply/Import/Undo/Revert): the field could be showing
  stale pre-restore text while the store has already moved on to a *different* flat value, and the
  un-forced rule would leave that stale text on screen even though `force=true` was passed (bypassing
  only the active-element guard, not this check) — e.g. Apply in Build mode restoring a flat plan
  before any ladder had been built left the top field on its old number even though every per-year
  row (once built) correctly showed the restored one. `force=true` now means the field is
  unconditionally resynced to `_daraByYearPanelDefault` whenever the store isn't by-year.

### Year list (unchanged)

**Build mode:** every year in `[firstYear, lastYear]` gets a group header row and DARA input:
- Funded years (actual TIPS) — no label suffix
- Gap years (2037–2039, TIPS not yet issued) — labelled `(gap)`; a custom DARA increases synthetic gap quantities and therefore bracket excess
- Future 30Y years (beyond last issued TIPS, currently 2056) — labelled `(30Y)`, shown only when `lastYear > maxTipsYear`; a custom DARA increases hypothetical future 30Y quantities and therefore future 30Y cover excess

**Rebalance mode:** every year in `[firstYear, lastYear]` gets a group header row and DARA input. Gap years within that range are labelled `(gap)`.

Years absent from the map fall back to the scalar DARA.

*Open question (flagged, not resolved here): whether the `(gap)`/`(30Y)` label suffixes remain
literal text next to the inline DARA element, or are dropped as redundant now that the row itself
already signals gap/Future-30Y years via the Gap/Future 30Y sub-row structure (5.0 §Sub-Row Logic).
Left to the code pass.*

### Why the maturing-proceeds/LMI breakdown stays in the popup

The old standalone panel surfaced (or was seen by some users as conflating) the maturing-proceeds-
vs-LMI breakdown for a year. That breakdown is **not** promoted into new inline columns on the table
row — it stays exactly where it already lives, the existing Amount Before / Amount After drill-down
popup (5.0 §Popup Routing, `amtBefore` / `amtAfter` / `amount`). This was a deliberate choice,
considered and rejected in favor of inline columns, so a future reader should not "fix" this by
re-adding columns for it.

## Before-State on Load (Rebalance)

The ladder output table renders **before Run is clicked**: as soon as holdings are loaded /
account(s) selected in Rebalance mode, Qty Before / Cost Before / Amount Before render for every
ordinary funded year (3.0 §Before-State Preview and Bracket-Year Excess Detection).

**`#table-controls` (Expand All / Collapse All, §Collapsible Groups below) is available as soon as
this before-state table renders** — the ladder table with its collapsible funded-year groups is
already fully visible pre-Run, so those two buttons are usable immediately too, not gated behind
Run. Only the genuinely **After**-dependent controls stay hidden until the user clicks Run
Rebalance and the After-side columns fill in: Export CSV, Export CUSIP/Qty, Trade Ticket, Duration
links, and `#ladder-stats-display` (Avg Yld / Avg SA Yld / Avg Mod Dur / Net Cash, §Row 3 above).
Build mode has no "Before" state and continues to render only after Run.

## Collapsible Groups

### Expand / Collapse All Buttons

Two secondary buttons — **Expand All** and **Collapse All** — are placed in `#table-controls`, a flex strip (`display:flex; gap:6px; padding:6px 16px 2px`) positioned directly above the output table divs (`#output`, `#build-output`), outside the form card. `#table-controls` is hidden (`display:none`) until a result is available, then shown as `display:flex`.

Styling: same secondary-button class as Export CSV buttons (`outline` variant or equivalent). Labels: `Expand All` / `Collapse All`.

### Group Header Row Visual Style

| Property | Value |
|---|---|
| Background | `rgba(255,255,255,0.06)` — slightly lighter than data rows |
| Font weight | `700` |
| Color | `#fff` |
| Cursor | `pointer` |
| Toggle glyph | `▼` (expanded) or `▶` (collapsed); positioned before the funded year integer with `margin-right: 6px` |
| Bracket year | Append `*` to the funded year integer; header row also gets `background: rgba(173,216,230,0.15)` (matches light-blue bracket theme, but muted for the header) |

### Child Row Visibility

When a group is collapsed (`data-expanded="false"`):
- All `.fy-child` rows with matching `[data-fy]` receive the `hidden` attribute.
- All `.acct-subrow` rows with matching `[data-fy]` receive the `hidden` attribute.
- The group header row itself remains visible at all times.

When expanded:
- `hidden` is removed from all matching `.fy-child` and `.acct-subrow` rows.
- Excess sub-rows (`.excess-subrow.fy-child`) are revealed along with the main TIPS rows — they are inseparable children of their group.
- Individual per-TIPS account expansion state (set via `style.display`) is preserved: rows that were individually collapsed before the group was collapsed remain individually hidden after expansion.

### Default State

**Bracket/cover-year groups render expanded; ordinary funded-year groups render collapsed**
(`_setDefaultGroupsExpanded`: `data-expanded = hdr.classList.contains('bracket')` for every
`fy-group-header` row) — the excess holdings that make a bracket/cover row worth a second look are
visible at a glance without an extra click, while the common case (an ordinary single-TIPS year) stays
compact. "Expand All"/"Collapse All" (above) still act on every group regardless of this default.

### Expand/Collapse State Survives a Rebalance Ladder Re-run

Re-running Rebalance Ladder rebuilds `#simple-table`'s `innerHTML` from scratch, which would
otherwise reset every group back to the default above and discard whatever the user had opened.
Before the rebuild, `_captureExpandedState(simpleEl)` snapshots each funded year's current
`data-expanded`; after, `_restoreOrDefaultGroupsExpanded(simpleEl, snapshot)` re-applies it,
falling back to the normal bracket/cover-year default only for a funded year absent from the
snapshot (e.g. the year range grew). This makes it possible to expand the one or two years of
interest, change Maturity preference or Allocation policy, re-run, and see the effect immediately
without re-expanding anything (2.0 §Within-Year Allocation Policy). Scoped to Rebalance's own
re-run (`renderOutput`) — Build's table and the pre-first-run Before-state preview
(3.0 §Before-State Preview and Bracket-Year Excess Detection) are unaffected.

### Totals Row

The tfoot totals row is always visible regardless of group expand/collapse state. Its values are unchanged — they reflect the full ladder totals including excess (as before).
