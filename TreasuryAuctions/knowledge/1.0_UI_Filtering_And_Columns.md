# 1.0 UI Filtering & Column Layout

## Dependencies
**Requires:** 0.0 Data Pipeline (field list, `_date`/`_dt` naming convention that `detectFmt()` keys off of)

**This file specifies the per-column filter behavior and column-width defaults for the main
historical table and the Tentative Schedule table. It exists because the raw data format and the
displayed format for dates diverge, and that divergence has caused two separate bugs — read this
before touching filter matching, date masking, or `colWidths`.**

---

## Date format divergence (root cause of prior bugs)

Row values for any `*_date`/`*_dt` field arrive from FiscalData/CSV as ISO `yyyy-mm-dd`. They are
**displayed** as `mm/dd/yyyy` via `fmtVal(v, 'date')`. The per-column filter input is a free-text
field the user types `mm/dd/yyyy` into — matching it against the raw ISO row value (instead of the
displayed value) is wrong and has broken filtering twice:

1. Plain substring filters must match against `fmtVal(rawVal, 'date')` (the displayed string), not
   the raw ISO string — otherwise the first `/` a user types can never appear in the ISO value and
   the filter zeroes out every row.
2. Range filters (`>`, `<`, `>=`, `<=`) must normalize an `mm/dd/yyyy` (or `m/d/yyyy`) target to ISO
   before comparing against `rVal.substring(0, 10)` — the row's raw ISO date, not its display form.

Both are handled in `getActiveRows()` in `src/app.js`. **Any change to filter matching must
preserve this: compare display-format text to display-format text, not display-format text to raw
ISO.**

---

## Auto-mask: digits → `mm/dd/yyyy`

Typing raw digits into any filter input on a field where `detectFmt(f) === 'date'` auto-inserts
slashes as you type (`10312026` → `10/31/2026`), matching the UX of the native `#dateFrom`/
`#dateTo` date pickers. Implemented once as `autoMaskDateFilter()` (top-level function, not a
method) — it strips a leading range operator (`>=`, `<=`, `>`, `<`) before masking the digits, then
re-prepends it, so range filters (`>07/16/2026`) mask correctly too.

**This same masking logic is wired into two separate places**, because the main table
(`renderTable()`) and the Tentative Schedule (`renderTentative()`) each own their own filter-input
`input` event listener:

- `renderTable()` → wires `filters[f]`
- `renderTentative()` → wires `tentFilters[f]`

Both call sites must call `autoMaskDateFilter()` the same way. See **Maintainability Note** below —
this duplication is a known candidate for consolidation, not an intentional design.

## Column widths (`colWidths`)

`colWidths` is a runtime-only `field → px` map (not persisted to `localStorage`; resets on page
reload). `table-layout: auto` means an unset field auto-sizes to the widest content across its
header label, filter input, and body cells.

Two ways a field gets a width:
1. **User drag-resize** — written directly into `colWidths[field]`, cleared by double-clicking the
   resizer handle (`delete colWidths[field]`, falls back to auto-sizing).
2. **`DEFAULT_COL_WIDTHS`** — applied at module load (`let colWidths = { ...DEFAULT_COL_WIDTHS }`)
   and **re-applied by the `resetColsBtn` handler** (`colWidths = { ...DEFAULT_COL_WIDTHS }`).

Currently: `issue_date` and `maturity_date` are pinned to `82px` — their header labels (`Issue
Date`, `Maturity`) are shorter than a fully-typed `mm/dd/yyyy` filter value, so auto-layout sized
them too narrow to show what the user typed. `auction_date` has no explicit default; its header
label (`Auction Date`) happens to be long enough to auto-size the column wide enough on its own.
That's incidental, not a guarantee — if `Auction Date`'s label is ever shortened, it will need the
same explicit-width treatment.

**Rule: any future default-width change belongs in `DEFAULT_COL_WIDTHS`, never as a bare assignment
into `colWidths`.** The `resetColsBtn` handler wipes `colWidths` back to `DEFAULT_COL_WIDTHS`
specifically — a one-off `colWidths[field] = …` elsewhere would look correct until the user clicks
"Reset defaults," at which point it silently reverts to auto-sizing.

## Maintainability Note (for a future session — not urgent, not yet actioned)

The main table and the Tentative Schedule table maintain **two parallel, hand-duplicated copies**
of: filter-input wiring (`input` event listener that reads `dataset.field`, masks dates, writes to
a filters object, toggles `.active`, debounces a re-render), and the filter-matching predicate
itself (`activeFilters.every(...)` against a row). They differ only in which state object they
write to (`filters` vs `tentFilters`) and which render function they debounce into
(`renderBody(cols)` vs `renderTentBody`).

This is exactly the kind of "copy kept in sync by hand" duplication the project's single-source-of-
truth rule warns against — a bug fix or feature added to one (e.g. this session's date-masking fix)
requires remembering to also apply it to the other, with no compiler or test to catch a missed
spot. A future refactor could extract a shared `wireFilterRow(thead, fieldsMeta, filterState,
onChange)` helper that both `renderTable()` and `renderTentative()` call, parameterized by which
state object and re-render function to use. Not done in this session — flagging so the next session
doesn't have to rediscover the duplication from scratch.
